# Feature Specification: Приёмка в реальном браузере (Playwright)

**Feature Branch**: `feature/speckit_intergation`

**Created**: 2026-11-11

**Status**: Draft

**Input**: Задача T28 из `docs/plan.md` («Прогон `examples/hello.html` в реальном браузере — приёмка T6, который пока подтверждён только сборкой бандла»).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Приёмочный пример `hello.html` исполняется в настоящем браузере (Priority: P1)

Разработчик запускает автоматический прогон, и настоящий браузер (не эмуляция DOM) открывает
`examples/hello.html`, подключает `dist/onescript.js` и исполняет `<one-script>` из `task.md`.
В консоли страницы появляются те же три строки, что ожидает исходное ТЗ:
«Привет, ты указал: Никита, Иванченко», «возраст больше 30», «Добро пожаловать, Никита твой возраст 38».

**Why this priority**: Это единственная проверка, которая доказывает, что браузерный контракт
(`<script src>`, `<one-script>`, `Сообщить()` → `console.log`) работает в реальной среде, а не
только на эмулированном DOM (`happy-dom`).

**Independent Test**: Страница `hello.html` открывается в Chromium, сообщения из `console.log`
собраны и совпадают с ожидаемыми, страница не содержит ошибок JavaScript.

**Acceptance Scenarios**:

1. **Given** собранный `dist/onescript.js`, **When** браузер открывает `examples/hello.html`,
   **Then** в консоли есть три ожидаемые строки в порядке исполнения.
2. **Given** та же страница, **When** код исполняется, **Then** ошибок в консоли (`pageerror`)
   нет, а содержимое `<one-script>` на странице не отображается.

---

### User Story 2 - Интерактивные демо работают в браузере (Priority: P2)

Разработчик проверяет не только вывод, но и интерактив: кнопка-счётчик увеличивает значение,
поле ввода зеркалирует текст, наведение меняет класс, DOM-элементы создаются из BSL.

**Why this priority**: `hello.html` не покрывает DOM-слой (`Документ`, `НаСобытие`), а именно он
проверялся только на `happy-dom`. Реальный браузер выявит различия событийной модели.

**Independent Test**: Каждая из страниц `counter.html`, `input.html`, `hover.html`, `dom.html`
открывается, действие пользователя эмулируется, ожидаемое состояние DOM проверяется.

**Acceptance Scenarios**:

1. **Given** `counter.html`, **When** пользователь дважды нажимает кнопку, **Then** в выводе `2`.
2. **Given** `input.html`, **When** вводится текст, **Then** зеркалирующий элемент содержит его.
3. **Given** `hover.html`, **When** курсор наведён и уведён, **Then** класс/стиль меняется и возвращается.
4. **Given** `dom.html`, **When** страница загружена, **Then** элементы, созданные из BSL, присутствуют в DOM.

---

### User Story 3 - Прогон воспроизводим и пригоден для повторного запуска (Priority: P3)

Прогон запускается одной командой, сам собирает то, что нужно, поднимает локальную раздачу
и не требует сети и ручных шагов; при падении даёт достаточно диагностики.

**Why this priority**: Проверка, которую нельзя повторить одной командой, не станет гейтом и
загниёт, как только перестанет быть новинкой.

**Independent Test**: На чистом клоне после `pnpm install` команда прогона завершается успехом
без ручной подготовки; при искусственной поломке страницы тест падает с понятным сообщением.

**Acceptance Scenarios**:

1. **Given** чистый клон с зависимостями, **When** выполняется команда e2e-прогона, **Then** сборка,
   сервер и браузер запускаются автоматически, по завершении сервер остановлен.
2. **Given** намеренно сломанная страница, **When** прогон выполняется, **Then** тест падает и
   выводит страницу/сообщение об ошибке, по которому локализуется причина.

### Edge Cases

- Браузер не установлен: команда должна подсказать шаг установки, а не падать с невнятной ошибкой.
- Порт локальной раздачи занят: прогон не должен зависать.
- Страница без `<one-script>`: прогон не падает, фиксирует отсутствие сценария.
- Медленная CI-машина: используется ожидание условия (появление текста/элемента), а не фиксированная пауза.
- Изменённый `dist/onescript.js`: прогон обязан использовать свежую сборку, а не закешированную.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Прогон MUST открывать страницы из `examples/` в реальном браузерном движке (Chromium headless), а не в эмуляции DOM.
- **FR-002**: Для `hello.html` MUST проверяться ровно три сообщения `console.log` из приёмочного сценария `task.md` (текст и порядок).
- **FR-003**: Для интерактивных страниц MUST эмулироваться действие пользователя и проверяться наблюдаемое состояние DOM: счётчик (`counter.html`), зеркалирование ввода (`input.html`), смена класса при наведении (`hover.html`), созданные из BSL элементы (`dom.html`).
- **FR-004**: Прогон MUST быть одной командой: сборка браузерного бандла, запуск локальной раздачи `examples/` и остановка раздачи по завершении выполняются автоматически.
- **FR-005**: Прогон MUST использовать только локальные файлы репозитория и не обращаться в сеть.
- **FR-006**: При падении прогон MUST сообщать, какая страница и какое ожидание не выполнены; MUST сохраняться артефакт для диагностики (лог консоли и/или снимок страницы).
- **FR-007**: Ошибки JavaScript на странице (`pageerror`) MUST считаться провалом прогона.
- **FR-008**: Прогон MUST не требовать изменения существующих демо-страниц и существующих `happy-dom` тестов; он дополняет их, а не заменяет.
- **FR-009**: Прогон MUST выполняться отдельной командой пакета, документированной в `README.md`, и не входить в обычный `pnpm test`.
- **FR-010**: Дополнительная зависимость для e2e-прогона MUST быть dev-only и не попадать в браузерный бандл и Node-библиотеку.

### Key Entities

- **Страница-сценарий**: HTML из `examples/`, открываемая браузером; хранит `<one-script>` и разметку для взаимодействия.
- **Ожидание**: проверяемое условие в браузере (текст в консоли, содержимое элемента, класс, количество узлов).
- **Артефакт диагностики**: лог консоли/снимок, сохраняемый при падении.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Прогон с одной командой проверяет 100% демо-страниц (`hello`, `dom`, `counter`, `input`, `hover`) и завершается успехом на чистой машине после установки зависимостей и браузера.
- **SC-002**: `hello.html` даёт ровно три ожидаемые строки консоли — совпадение 3 из 3, порядок сохранён.
- **SC-003**: Намеренная поломка любого из проверяемых элементов приводит к падению прогона с указанием страницы — 100% случаев.
- **SC-004**: Прогон укладывается в 2 минуты на обычной машине разработчика.
- **SC-005**: Существующий набор тестов (`pnpm test`) и браузерная/Node-сборки остаются зелёными; число регрессий — ноль.

## Assumptions

- Используется Playwright с Chromium: минимальный набор, достаточный для проверки DOM-контракта; другие браузеры — по мере необходимости.
- Раздача страниц — локальный статический сервер над собранным `dist/` (как `pnpm demo`), а не `file://`: так ближе к реальному развёртыванию.
- Браузер устанавливается отдельным шагом (`playwright install chromium`), который документируется; сам прогон его не скачивает.
- Скриншоты/логи — только при падении (минимум диагностики, без «архива на каждый запуск»).
- Вне объёма: кроссбраузерная матрица (Firefox/WebKit), визуальное регрессионное сравнение, нагрузочные проверки.
- Зависимость от T6–T49: страницы и бандл уже существуют; новая работа — только автоматизация приёмки, без изменения функциональности движка.
