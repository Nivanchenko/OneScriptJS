# Feature Specification: Редакторные инструменты `.osjs` — грамматика, LSP-сервер (линтер, подсказки, подсветка)

**Feature Branch**: `feat/linter`

**Created**: 2026-11-11

**Status**: Implemented (тесты + smoke + ручная проверка в Neovim 0.12.2)

**Input**: Запрос владельца проекта: «начни готовить спеку по этому требованию» — по заметке
[`specs/013-osjs-format/spec.md`](../013-osjs-format/spec.md), раздел «Следующая работа (вне
объёма 013): линтер / language server / плагин VS Code». Уточнения владельца:

1. «хочу лсп сервер, грамматики, и тд. расширение vscode потом» — в объёме этой спеки
   редакторо-независимые артефакты (грамматика/описание языка) и **LSP-сервер**; расширение
   VS Code как тонкая обёртка — следующая работа.
2. «Синтаксис, очевидные семантические проверки, и подсветка (не знаю как правильно это
   называется в протоколе lsp)» — диагностика включает синтаксис и очевидные семантические
   проверки, без стилевых правил; подсветка от сервера — это LSP `semanticTokens`
   (semantic highlighting), она входит в объём в дополнение к декларативной грамматике.

## Context

`specs/013-osjs-format` отделила наш формат `.osjs` от чужого `.os`: в смешанном проекте
`.os` остаётся у расширения ванильного OneScript, `.osjs` — наш. Но `.osjs` пока не
обслуживает ни один редактор: нет подсветки, нет проверок на лету, нет подсказок.
Разработчик, пишущий для OneScriptJS, узнаёт об ошибке только при запуске скрипта.

Решение по границам: сначала — **редакторо-независимое ядро инструментов**: описание языка
(TextMate-грамматика + конфигурация языка + метаданные привязки `*.osjs` → `osjs`) и
**LSP-сервер по stdio**. Их потребитель — любой редактор с поддержкой TextMate/LSP
(VS Code, Neovim, Zed, Sublime и т.п.). Тонкий клиент VS Code (манифест, language
contribution, установка из `.vsix`) — отдельная следующая работа: он только подключит уже
готовые грамматику и сервер, поэтому в эту спеку не входит.

Ключевое ограничение: **у движка уже есть свой лексер и парсер на TypeScript**
(`src/lexer`, `src/parser`, `src/ast`), и инструменты должны опираться на них, а не на второй
анализатор. Сервер — оболочка слоя `src/node`-типа: ядро движка не получает зависимостей от
LSP/Node, браузерная сборка не меняется.

Что известно о текущем состоянии движка (влияет на выполнимость требований, но не диктует
реализацию):

- Лексер отдаёт токены с начальной позицией (строка/колонка, с 1) без длины/смещения;
  комментарии и директивы препроцессора в поток токенов не попадают.
- В AST у узлов есть только начальная позиция; для диапазона подчёркивания нужны позиции
  конца узла.
- Парсер бросает исключение на **первой** синтаксической ошибке и не отдаёт частичный AST,
  поэтому «показать все ошибки файла» и «не падать на недописанном коде» требуют
  восстановления после ошибок — без изменения семантики исполнения.
- Набор языка и stdlib выводим из кода: ключевые слова RU/EN, `registerAlias`/`registerType`/
  `registerGlobal`/`registerEnum`; `scripts/check-api-docs.mjs` уже собирает имена API для
  сверки со справочником. Отдельного ручного списка для подсказок быть не должно.
- LSP-зависимостей и серверной обвязки в репозитории нет; расширения VS Code нет; `.os` мы
  не заявляем (013, FR-002).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - `.osjs` опознаётся и подсвечивается в редакторе (Priority: P1)

Разработчик подключает в свой редактор наши артефакты описания языка (TextMate-грамматика
`source.osjs`, конфигурация скобок/комментариев/фолдинга, метаданные «`*.osjs` — это язык
`osjs`») и открывает `.osjs`. Ключевые слова, операторы, строки (включая многострочные с
`|`), числа, даты, комментарии, директивы препроцессора и аннотации подсвечены; скобки и
кавычки парные, `//` — строчный комментарий, `#Область`/`#Если` складываются по маркерам,
тела процедур/функций — механизмом отступов редактора. Файлы `.os` эти артефакты не
заявляют и не трогают.

**Why this priority**: Подсветка нужна раньше сервера: она работает без процесса, даёт
ценность сразу и задаёт главную границу «`.osjs` — наш формат, `.os` — чужой». Она же —
база для тех редакторов, где LSP не подключён.

**Independent Test**: автоматическая проверка scope на фикстуре со всеми конструкциями из
FR-002 (без запуска редактора); отдельно — метаданные привязки не содержат `*.os`.

**Acceptance Scenarios**:

1. **Given** `.osjs` с конструкциями `Если … Тогда … КонецЕсли`, `Для … По`,
   `Попытка … Исключение`, **When** файл открыт в редакторе с TextMate-грамматикой,
   **Then** ключевые слова RU/EN, операторы, строки, числа, даты, комментарии и `#Область`
   визуально отличаются от идентификаторов.
2. **Given** многострочная строка с `|` и комментарии `//` внутри, **When** файл открыт,
   **Then** продолжения строки подсвечены как строка, а не как код.
3. **Given** `Асинх Функция` и оператор `Ждать`, **When** файл открыт, **Then** `Асинх` и
   `Ждать` подсвечены как ключевые слова нашего диалекта.
4. **Given** блок `#Область … #КонецОбласти` или `#Если … #КонецЕсли`, **When** пользователь
   сворачивает регион, **Then** блок складывается целиком по маркерам; тела методов
   складываются механизмом отступов редактора (без LSP).
5. **Given** проект с `.os` и `.osjs`, **When** применяются наши артефакты описания языка,
   **Then** `*.os` не сопоставлен нашему языку, а `.osjs` — сопоставлен.

### User Story 2 - LSP-сервер: ошибки видны сразу, без запуска скрипта (Priority: P2)

Разработчик подключает наш LSP-сервер (запуск по stdio) к своему редактору и печатает код.
Синтаксические ошибки и очевидные семантические проблемы (неизвестное имя, неверное число
аргументов у известной функции) подчёркиваются в момент ввода: точная позиция (строка и
колонка), несколько ошибок одновременно, список в панели Problems, устаревшие диагностики
исчезают после исправления. Недописанный код (`Если` без `Тогда`, незакрытая строка, мусор
посреди выражения) не вешает сервер и не роняет клиент.

**Why this priority**: Это ядро «линтера»: главная польза — узнать об ошибке до запуска.
Сервер использует тот же парсер, что и движок, поэтому диагностика совпадает с реальным
разбором, а не с приблизительной грамматикой.

**Independent Test**: интеграционный тест по stdio с минимальным LSP-клиентом: `initialize`
→ `didOpen` файла с тремя ошибками → приходит `publishDiagnostics` со всеми тремя и с
корректными диапазонами; `didChange` с исправлением → приходит пустой набор; недописанный
код → ошибка разбора, сервер жив.

**Acceptance Scenarios**:

1. **Given** файл с ошибкой разбора на строке 5, **When** сервер получил уведомление об
   открытии/изменении, **Then** в течение 1 секунды публикуется диагностика с диапазоном на
   строке 5 и колонке ошибки.
2. **Given** файл с тремя независимыми ошибками, **When** он открыт, **Then** публикуются
   все три диагностики, а не только первая.
3. **Given** диагностика на строке 5, **When** ошибка исправлена, **Then** публикуется
   обновлённый набор без неё в течение 1 секунды.
4. **Given** неизвестное имя или вызов известной функции с неверным числом аргументов,
   **When** файл проверен, **Then** публикуется семантическая диагностика с пояснением;
   стилевых правил (длина строки, неиспользуемые переменные) диагностика не содержит.
5. **Given** пользователь печатает незаконченное выражение, **When** документ в невалидном
   состоянии, **Then** сервер отвечает диагностикой разбора, не падает и не перестаёт
   обрабатывать последующие изменения.
6. **Given** язык документа не `osjs` (клиент прислал другой languageId), **When** сервер
   получает документ, **Then** он не публикует наши диагностики.

### User Story 3 - Подсказки: что можно написать и что означает символ (Priority: P3)

Разработчик набирает `Сооб` и получает `Сообщить`/`Message` с сигнатурой; набирает `Если` —
получает `Тогда`; после `Массив.` (когда тип выражения однозначен) — методы массива;
наводит мышь на глобальную функцию/тип — видит подпись и краткое описание из справочника
движка. В строках и комментариях подсказок языка нет; сервер не предлагает имён, которых
нет в движке.

**Why this priority**: Автокомплит и hover — основная обещанная ценность language server,
но она опирается на уже работающие разбор и диагностику (US2) и на единый каталог API.

**Independent Test**: интеграционный тест: `completion` в позиции `Сооб` содержит
`Сообщить` и `Message`; `completion` после `Массив.` содержит методы `Массив`; `hover` на
`Сообщить(` возвращает сигнатуру и описание, совпадающие с `docs/reference.md`; в строке
подсказок нет.

**Acceptance Scenarios**:

1. **Given** пустая строка в `.osjs`, **When** клиент запрашивает completion для префикса
   `Сооб`, **Then** в ответе есть глобальная функция `Сообщить` (и английский алиас
   `Message`) с сигнатурой.
2. **Given** фрагмент `М = Новый Массив; М.`, **When** запрошен completion после точки,
   **Then** предлагаются методы/свойства `Массив`, а не случайный набор.
3. **Given** курсор внутри строкового литерала или комментария, **When** запрошен
   completion, **Then** подсказки языка не возвращаются.
4. **Given** курсор на `Сообщить(`, **When** запрошен hover, **Then** видны имя, параметры и
   краткое описание, совпадающие с `docs/reference.md`.
5. **Given** локальная переменная или метод, объявленные в файле, **When** запрошен
   completion по их префиксу, **Then** они возвращаются.

### User Story 4 - Подсветка от сервера и навигация по файлу (Priority: P4)

Разработчик получает семантическую подсветку (LSP `semanticTokens`): ключевые слова,
строки, числа, даты, комментарии, директивы, аннотации, имена функций и переменных
подсвечиваются по разобранному коду, а не только по регэкспам; после правок подсветка не
съезжает. В Outline видны методы и `#Область`, из вызова метода можно перейти к его
определению, из `#Использовать "lib/Модуль.osjs"` — открыть файл модуля.

**Why this priority**: В заметке 013 semantic tokens, переходы и символы документа отмечены
как «позже» — это полезное, но не блокирующее дополнение к минимуму. Владелец отдельно
подтвердил, что «подсветка» нужна; в LSP это называется `semanticTokens`, и она входит в
объём этой спеки, но последней очередью.

**Independent Test**: интеграционный тест: для фикстуры сервер возвращает semantic tokens
ожидаемых типов на ожидаемых диапазонах; `documentSymbol` возвращает методы и регионы;
`definition` из вызова ведёт на объявление метода; `definition` из `#Использовать` —
на файл модуля.

**Acceptance Scenarios**:

1. **Given** `.osjs` с ключевыми словами, строками, числами, комментариями, директивами и
   аннотациями, **When** клиент запрашивает semantic tokens, **Then** каждый класс лексем
   получает свой token type на корректном диапазоне.
2. **Given** документ изменён (добавлена строка), **When** semantic tokens запрошены заново,
   **Then** диапазоны соответствуют новому тексту и не съезжают.
3. **Given** файл с двумя методами и двумя `#Область`, **When** запрошены символы документа,
   **Then** в ответе есть методы и регионы с корректными позициями.
4. **Given** вызов локального метода, **When** запрошено определение, **Then** возвращается
   позиция объявления метода.
5. **Given** `#Использовать "lib/Модуль.osjs"` с существующим файлом, **When** запрошено
   определение, **Then** возвращается `Location` файла модуля.

### Edge Cases

- `.os` в смешанном проекте: наши артефакты не привязывают `*.os` к языку `osjs`, сервер не
  обслуживает документы с чужим languageId; конфликта за суффикс нет (013, Context).
- `Асинх`/`Ждать` — контекстные слова: декларативная грамматика может подсвечивать их всегда,
  даже когда это идентификатор; серверные подсказки/диагностики обязаны учитывать контекст.
- Недописанный код: тысячи промежуточных ошибок не должны вешать сервер; количество
  публикуемых диагностик ограничивается, сервер продолжает обрабатывать изменения.
- Документ без файла на диске (untitled-буфер, languageId `osjs`): диагностика и подсказки
  работают, потому что не требуют файла; `#Использовать`-переходы в таком случае ограничены.
- `#Использовать` на несуществующий файл: это не ошибка разбора; семантическая диагностика
  таких путей в объём не входит, кроме перехода к определению (US4).
- BOM, CRLF, кириллица: позиции/диапазоны в LSP считаются в UTF-16 code units, как требует
  протокол; диагностика не съезжает на кириллице и эмодзи.
- Огромный файл (десятки тысяч строк): сервер остаётся отзывчивым, даже если диагностика
  приходит с задержкой; клиент не блокируется.
- Клиент не поддерживает заявленную возможность (например, нет semantic tokens): сервер
  объявляет capabilities корректно и продолжает работать в урезанном наборе функций.
- Клиент прислал запрос для документа, который не открыт, или устаревшую версию: сервер
  отвечает корректной ошибкой протокола/игнорирует устаревшее изменение, не падая.
- Серверный процесс упал/перезапущен: редактор продолжает работать (подсветка грамматикой
  остаётся), данные на диске не теряются; перезапуск сервера восстанавливает диагностику.
- Сообщения диагностик — на русском (язык проекта и справочника), с позицией; локализация
  интерфейса не входит в первую версию.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Артефакты описания языка ДОЛЖНЫ привязывать к языку `osjs` только `*.osjs`
  и НЕ ДОЛЖНЫ заявлять `*.os` (граница из 013, FR-002).
- **FR-002**: Грамматика подсветки ДОЛЖНА покрывать лексику языка: ключевые слова и
  операторы RU/EN; константы `Истина`/`Ложь`/`Неопределено`/`Null`; числа; строки, включая
  многострочные с `|`; даты (`'ГГГГММДД'` и аналоги); комментарии `//`; директивы
  препроцессора `#Если`/`#ИначеЕсли`/`#Иначе`/`#КонецЕсли`, `#Область`/`#КонецОбласти`,
  `#Использовать`; аннотации `&Имя`; расширения диалекта `Асинх`/`Ждать`.
- **FR-003**: Конфигурация языка ДОЛЖНА давать: автозакрытие и парную подсветку `()`, `[]`,
  кавычек; `//` как строчный комментарий; word pattern с кириллицей; сворачивание по
  маркерам для `#Область…КонецОбласти` и `#Если…КонецЕсли`. Тела процедур/функций
  складываются механизмом отступов редактора; LSP `foldingRange` в объём не входит.
- **FR-004**: LSP-сервер ДОЛЖЕН запускаться отдельным процессом и общаться по stdio
  (LSP over stdio, framing по протоколу), корректно проходить жизненный цикл
  `initialize` → работа → `shutdown`/`exit`, объявлять только реально поддерживаемые
  возможности и синхронизировать документы (`didOpen`/`didChange`/`didClose`).
- **FR-005**: Диагностика ДОЛЖНА работать в реальном времени: точная позиция (строка и
  колонка), диапазон выделения, все ошибки файла одновременно, `publishDiagnostics` с
  очисткой устаревших наборов при исправлении.
- **FR-006**: Диагностика ДОЛЖНА включать: (а) синтаксические ошибки разбора; (б) очевидные
  семантические проверки — неизвестное имя/метод, неверное число аргументов у известной
  функции; стилевые правила (длина строки, неиспользуемые переменные и т.п.) НЕ входят.
- **FR-007**: Диагностика файла ~1000 строк ДОЛЖНА укладываться в 1 секунду; после правки
  результаты обновляются не дольше 1 секунды; сервер не должен блокировать клиент дольше
  этого бюджета.
- **FR-008**: Автодополнение (LSP completion) ДОЛЖНО предлагать: ключевые слова и операторы
  RU/EN; глобальные функции, типы и перечисления stdlib с сигнатурами; локальные переменные,
  параметры и методы документа; члены объекта, когда тип выражения однозначно определим;
  фильтровать по набранному префиксу; не возвращать подсказки внутри строк и комментариев;
  не предлагать имён, которых нет в движке.
- **FR-009**: Hover ДОЛЖЕН возвращать сигнатуру и краткое описание для глобальных функций,
  типов, методов и свойств stdlib, для локальных символов, а также краткое пояснение для
  контекстных слов `Асинх`/`Ждать`.
- **FR-010**: Сервер ДОЛЖЕН поддерживать семантическую подсветку (LSP `semanticTokens`):
  классы лексем (ключевые слова, операторы, числа, строки, даты, комментарии, директивы,
  аннотации, имена функций/переменных) получают собственные типы на корректных диапазонах;
  после правок токены не съезжают; при отсутствии поддержки у клиента сервер работает без
  этой возможности, а декларативная грамматика продолжает подсвечивать файл.
- **FR-011**: Сервер ДОЛЖЕН возвращать структуру документа (методы, `#Область`) и
  поддерживать переход к определению локального метода/переменной и файла из `#Использовать`.
- **FR-012**: Данные для автодополнения, hover и семантических проверок по stdlib ДОЛЖНЫ
  строиться из объявлений самого движка (единый источник с `docs/reference.md`); отдельный
  ручной список запрещён, рассинхронизация ловится автоматической проверкой.
- **FR-013**: Сервер ДОЛЖЕН быть отказоустойчивым: недописанный/битый код даёт диагностику,
  а не падение или зависание; сбой одной возможности не ломает остальные; после перезапуска
  сервера всё восстанавливается без потери данных.
- **FR-014**: Сервер ДОЛЖЕН быть самодостаточным: работать офлайн, не скачивать внешний
  сервер или данные в рантайме, не отправлять телеметрию; запускаться из локальной сборки
  репозитория без обязательных внешних сервисов.
- **FR-015**: Инструменты НЕ ДОЛЖНЫ менять семантику исполнения и публичный API движка;
  ядро (`src/lexer`, `src/parser`, `src/ast`, `src/runtime`, `src/stdlib`) не получает
  зависимостей от LSP и Node-специфичных API; второй анализатор (tree-sitter и т.п.) не
  вводится; используются существующие лексер и парсер (конституция, принципы II и IV).
- **FR-016**: Если для диагностики требуется расширить парсер (позиции конца узлов,
  восстановление после ошибок), это ДОЛЖНО сохранять принятое поведение разбора и исполнения
  и покрываться тестами; красных тестов движка быть не должно.
- **FR-017**: ДОЛЖНЫ быть обновлены `README.md` (как запустить сервер и подключить
  грамматику), появиться пример `.osjs` для ручной проверки, `docs/architecture.md` (новый
  слой инструментов) и `docs/status.md` (строка спеки 014); при необходимости — `AGENTS.md`.
- **FR-018**: Тонкий клиент VS Code (манифест, language contribution, установка из `.vsix`,
  Marketplace) НЕ входит в эту спеку: он появится отдельной работой поверх готовых
  грамматики и сервера. Выбор редактора не должен влиять на содержимое артефактов.

### Key Entities

- **Language id `osjs`** — идентификатор языка и единственная привязка к `*.osjs`.
- **Грамматика подсветки** — декларативное описание лексики и scope `source.osjs`.
- **Конфигурация языка** — скобки, комментарии, word pattern, правила фолдинга.
- **LSP-сервер** — процесс по stdio, объявленные capabilities, версии документов, набор
  возможностей (диагностика, completion, hover, semantic tokens, symbols, definition).
- **Диагностика** — ошибка/предупреждение с диапазоном (строка/колонка), сообщением,
  severity и источником; набор диагностик принадлежит версии документа.
- **Каталог API движка** — глобальные функции, типы, перечисления, методы и свойства с
  сигнатурами; единый источник для completion, hover, семантических проверок и справочника.
- **Semantic token** — тип и диапазон лексемы, вычисленный по разобранному коду.
- **Модель документа** — текст + разобранные символы (методы, переменные, регионы);
  пересобирается при изменении версии документа.
- **Артефакт поставки** — грамматика, конфигурация, метаданные языка и собранный сервер;
  потребитель — произвольный LSP/TextMate-совместимый редактор.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Автоматическая проверка грамматики на фикстуре подтверждает scope не менее чем
  для 20 различных конструкций языка (ключевые слова RU/EN, строки, многострочные строки,
  числа, даты, комментарии, директивы, аннотации, `Асинх`/`Ждать`), и ни одна из них не
  остаётся обычным идентификатором.
- **SC-002**: Метаданные языка сопоставляют `*.osjs` с `osjs` и не сопоставляют `*.os`;
  сервер не публикует наших диагностик для документов с чужим languageId.
- **SC-003**: Интеграционный тест по stdio проходит жизненный цикл LSP; синтаксическая ошибка
  появляется на правильной строке/колонке не позже чем через 1 секунду; при трёх независимых
  ошибках публикуются все три; после исправления набор очищается не позже чем через 1 секунду.
- **SC-004**: Семантическая диагностика срабатывает на неизвестное имя и на неверное число
  аргументов известной функции; стилевых диагностик нет.
- **SC-005**: Файл в 1000 строк диагностируется не дольше 1 секунды, и правки не вызывают
  заметных (более 1 секунды) зависаний сервера.
- **SC-006**: Результат completion для префикса `Сооб` содержит `Сообщить` и `Message`;
  после `Массив.` — методы `Массив`; в строке/комментарии подсказок нет; hover на
  `Сообщить(` возвращает сигнатуру, совпадающую с `docs/reference.md`.
- **SC-007**: Semantic tokens покрывают классы лексем из FR-010 на ожидаемых диапазонах и не
  съезжают после вставки/удаления строк; `documentSymbol` и `definition` возвращают
  ожидаемые позиции/файлы.
- **SC-008**: Файл, в котором одновременно 100+ ошибок разбора, обрабатывается без падения
  сервера; 10 минут непрерывных правок в недописанном коде не приводят к падению/зависанию,
  а перезапуск сервера восстанавливает работу.
- **SC-009**: Свежий запуск сервера и подключение артефактов работают без доступа к сети;
  внешних скачиваний и телеметрии нет.
- **SC-010**: `pnpm typecheck && pnpm test` зелёные; новые зависимости (если появились)
  обоснованы; сборка сервера и артефактов воспроизводится одной документированной командой.
- **SC-011**: Документация обновлена: README объясняет запуск сервера и подключение
  грамматики в редакторе, пример `.osjs` воспроизводит сценарии US1–US4,
  `docs/architecture.md` и `docs/status.md` отражают новый слой.

## Out of Scope

- Тонкий клиент VS Code: манифест расширения, language contribution, установка из `.vsix`,
  публикация в Marketplace, автообновление — следующая работа поверх этой спеки (ответ
  владельца: «расширение vscode потом»).
- Инструменты для `.os` и вообще для ванильного OneScript — у него свои линтеры и расширение.
- Форматирование, rename, рефакторинг, quick fixes, signature help, inlay hints, code lens —
  не входят в первую версию.
- LSP `foldingRange`: регионы `#Область`/`#Если` обслуживаются маркерами грамматики,
  тела методов — механизмом отступов редактора. Отдельный folding-провайдер не нужен.
- Стилевые правила линтера (неиспользуемые переменные, длина строки и т.п.).
- Диагностика `[Node]`-API как ошибки в браузерных файлах: для этого нужен явный выбор
  целевой среды у файла/проекта, отдельное решение.
- Второй анализатор (tree-sitter) и отдельный формат AST для инструментов.
- CLI-режим линтера (аналог `oscript -check`): CLI не расширяется сверх нужд отладки
  (конституция, «Технологические ограничения»).
- Настройки и конфигурация правил: первая версия работает без конфигурации.

### Заметки на будущее (не анализировать в 014)

  Там возможны оговорки и наложение на другие инструменты/расширения; это отдельная

## Assumptions

- **Редакторо-независимый слой первым.** Поставка — артефакты описания языка и LSP-сервер;
  клиент VS Code добавится позже и не должен требовать изменений в них. Проверка — тестами
  грамматики и протокольными интеграционными тестами, без запуска VS Code.
- **Грамматика — вендоренная MIT-копия `1c-syntax`.** База — `1c-syntax/vsc-language-1c-bsl`
  (`syntaxes/1c.tmLanguage.json`, лицензия MIT, © 2015 xDrivenDevelopment), зафиксированная
  по коммиту; копия лежит в `editors/osjs/` с `NOTICE.md` (копирайт + текст лицензии +
  список правок). Root scope переименовывается в `source.osjs`, `fileTypes` — только
  `["osjs"]`, добавляется диалект и ключевые слова движка; platform-specific `support.*`
  из upstream не переносятся (имена stdlib — зона semantic tokens). Синхронизация с
  upstream — вручную, по мере необходимости (зафиксировано в NOTICE).
- **`language-configuration.json` — де-факто VS Code-формат** (VS Code и его форки; другие
  редакторы используют собственные адаптеры). Переносимы между редакторами грамматика и
  `languages.json`; для не-VS Code редакторов конфигурация скобок/комментариев/фолдинга
  задаётся их собственными средствами.
- **«Подсветка» в ответе владельца = LSP `semanticTokens`** (семантическая подсветка от
  сервера) в дополнение к декларативной TextMate-грамматике; владелец подтвердил трактовку,
  semantic tokens входят в объём (US4), но последней очередью.
- **Лексер и парсер переиспользуются.** Для диагностики парсер дополняется позициями конца
  и восстановлением после ошибок; это внутренняя работа, не меняющая язык и семантику.
- **Полный репарс файла на каждом изменении достаточен** (в обсуждении замер ~1,7 мс на 1000
  строк); инкрементальный разбор не требуется.
- **Данные каталога API доступны на этапе сборки** из исходников движка; рантайм-рефлексия
  движка в сервере не нужна.
- **Сервер — новая оболочка уровня `src/node`**, а не часть ядра: браузерная сборка не
  меняется, зависимости от LSP/Node в ядро не проникают.
- **Конфигурация не обязательна.** Никаких настроек, без которых инструмент не работает.
- **`.osjs` без файла на диске** (untitled-буфер с languageId `osjs`) поддерживается.
- **Настоящая спека не меняет браузерный рантайм.** Приёмка «в браузере» (конституция V)
  к ней неприменима: проверяются тесты грамматики и протокольные тесты сервера; это
  ограничение фиксируется в `docs/status.md`.
- **Бюджеты производительности** измеряются на обычном dev-ноутбуке для файла ~1000 строк;
  для файлов на порядок больше допускается задержка диагностики при сохранении
  отзывчивости.
- **Сообщения диагностик — на русском**, как и остальная документация проекта; локализация
  интерфейса не входит в первую версию.
