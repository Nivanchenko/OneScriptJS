# Research: редакторные инструменты `.osjs`

Решения, принятые до дизайна (Phase 0). Формат: решение → почему → что рассматривалось
как альтернатива. Внешние факты без ссылок — из практики LSP/TextMate; ссылки на upstream
артефактов указаны там, где решение зависит от лицензии/раскладки.

## D1. LSP SDK: официальный `vscode-languageserver`

**Решение**: devDependencies (бандлятся в сервер, рантайм-зависимостей у пакета нет):
- `vscode-languageserver@11.0.0` (CJS-only, subpath `./node` под condition `node`),
- `vscode-languageserver-textdocument@1.0.16` (dual ESM/UMD),
- `vscode-jsonrpc@10.0.0` — явно, для тестовой клиентской стороны (strict pnpm не хойстит
  транзитивные пакеты),
- протокол/типы — транзитивные, отдельно не объявляются.
Версии — точные (без `^`): проверены на Node 24.22 / Vite 6.4.5 / tsc 5.9 под
`strict`/`verbatimModuleSyntax`/`moduleResolution: Bundler`; Node ESM делает named-import
из CJS через `cjs-module-lexer`, поэтому `import { createConnection } from
'vscode-languageserver/node'` работает без бандлера. Бандл: `dist/lsp/server.mjs` ≈ 425 КБ
(62 КБ gzip), 150 модулей, сборка ~0,3 с.

**Почему**: LSP — это большой внешний протокол (framing, JSON-RPC, диспетчеризация,
жизненный цикл, типы параметров/результатов, синхронизация документа). Официальный SDK —
«стандартная библиотека» платформы LSP, используется практически всеми TS-серверами
(typescript-language-server, yaml-language-server, svelte/astro/vscode-eslint); он убирает
целый класс ошибок, не относящихся к продукту. Лестница решений: шаг «использовать
платформенную возможность», а не «писать свой протокол».

**Альтернативы**:
- *Собственный JSON-RPC/stdio*: прототип ~150 строк TS прошёл простой клиент, но не
  покрывает ParseError на битый JSON, state machine после `shutdown`, `$/cancelRequest`,
  backpressure, типизированные результаты/params; тесты на протокол вместо тестов на
  продукт; ошибки framing (длина в **байтах** UTF-8, разрывы чанков по `\r\n\r\n`, порядок
  сообщений) дороги. Отклонено.
- *Только `vscode-jsonrpc` + ручные типы*: framing даром, но lifecycle/ошибки/неизвестные
  методы — сами; выигрыш не оправдан.
- *Не бандлить SDK (`external`)*: сервер требует `node_modules` рядом с `dist/`, ломает
  self-contained/офлайн-поставку и усложняет будущий клиент VS Code; если когда-то
  понадобится — пакеты переезжают в `dependencies`.
- *Второй парсер/tree-sitter* — запрещён спекой (FR-015).

**Vite-настройки (обязательны)**:
- `resolve.conditions: ['node']` — без этого build падает: `No known conditions for
  "./node" specifier`;
- `external: [/^node:/, ...builtinModules]` — иначе Vite молча подменяет bare-builtins
  (`path`, `fs`, `url`, `net`, …) browser-заглушками, сборка «зелёная», падение на редкой
  ветке SDK (trace, IPC/socket, file-URI helpers). Митигация — smoke-тест собранного бандла.

## D2. Диагностика: push, а не pull

**Решение**: `textDocument/publishDiagnostics` (push) со сменой полного набора на
изменение документа.

**Почему**: работает во всех LSP-клиентах, естественно ложится на «одна версия документа —
один набор», не требует реализации `textDocument/diagnostic` (LSP 3.17 pull) и связанной
семантики `resultId`/`unchanged`, `relatedDocuments`, `workspace/diagnostic/refresh`. Для
одного документа разницы в UX нет. Смешивать модели нельзя: клиент с pull может
игнорировать push — поэтому `diagnosticProvider` **не** объявляется.

**Версии и порядок**: публиковать синхронно в `didOpen`/`didChange` (полный анализ ~2 мс),
всегда с `version` из params; `didClose` — пустой набор; `languageId !== 'osjs'` — не
публиковать. Синхронный анализ ⇒ гонок версий нет; при появлении асинхронного анализа —
guard `version < current → drop`.
`shortcut: sync publish, debounce если файлы > 10 000 строк.`

**Альтернативы**: pull-диагностика — современнее и даёт клиенту контроль частоты, но
поддержка хуже (часть клиентов рекламирует capability без реализации), а выигрыш для
одиночного файла незначителен; можно добавить позже, не меняя правила.

## D3. Синхронизация — Full, позиции — UTF-16

**Решение**: `textDocumentSync.change = 1` (Full), `positionEncoding = 'utf-16'`.

**Почему**: полный репарс уже дёшев (в обсуждении ~1,7 мс на 1000 строк), инкрементальные
range-изменения не дают выигрыша и добавляют состояние/краевые случаи (CRLF, суррогатные
пары). UTF-16 — кодировка по умолчанию LSP и совпадает с индексацией JS-строк: колонки
лексера (счёт code units) конвертируются в LSP-позиции вычитанием 1 без пересчёта.
`shortcut: клиенту, предложившему только utf-8, всё равно отвечаем UTF-16 (таких клиентов
нет; конверсия — позже).`

**Альтернативы**: Incremental sync — отложено; UTF-8/UTF-32 — клиенты вправе предложить,
но сервер объявляет UTF-16 и другие не поддерживает.

## D4. Толерантный анализ: аддитивный режим, `parse()` не меняется

**Решение**: в `src/parser` и `src/lexer` добавляются отдельные толерантные entry points:
- лексер: ошибки (незакрытая строка/дата, неожиданный символ) → список ошибок + продолжение;
- `parse(tokens)` — прежнее поведение (бросает на первой ошибке) — **не меняется**;
- `parseTolerant(tokens)` → `{ program, errors }`: ошибки собираются, восстановление на
  границах операторов/блоков (пропуск до `;`, закрывающего ключевого слова, начала метода),
  состояние (`methodKind`, `loopDepth`, `exceptDepth`, `inAsync`) восстанавливается через
  `try/finally`;
- препроцессор: опциональный толерантный режим для ошибок директив.

**Почему**: движку нужен строгий разбор (ошибка = исключение, как в эталоне), инструментам —
все ошибки и частичный AST. Разделение режимов сохраняет регресс движка и принцип III.

**Альтернативы**: сделать парсер всегда толерантным — меняет контракт движка и все
вызывающие; отдельный парсер для инструментов — запрещён (FR-015, конституция IV).

## D5. Диапазоны токенов и trivia

**Решение**: расширить `Token` полями конца (`endLine`/`endColumn`, 1-based, UTF-16);
комментарии эмитировать только по опции (`includeTrivia`) новым типом `Comment` — поведение
`tokenize()` по умолчанию не меняется. Препроцессорные токены уже есть (`Preprocessor`);
из trivia же берутся пары `#Область`/`#КонецОбласти` для outline (не из препроцессора).
Многострочные строки для semantic tokens разбиваются на сегменты по строкам.

**Почему**: LSP-диапазоны требуют конец; диагностике нужен диапазон offending-токена;
semantic tokens хотят комментарии и директивы, но парсер не должен их видеть. Опция
trivia — минимальное изменение с сохранением поведения.

**Альтернативы**: вычислять конец по `lexeme` в потребителе (дублирование логики на всех
вызовах, ошибки на многострочных строках); отдельный «подсветочный» лексер — дублирование.

## D6. Каталог API: из `docs/reference.md`, генерация + drift-тест

**Решение**: `scripts/build-api-catalog.mjs` парсит таблицы справочника (функции, методы,
свойства, значения перечислений, описания, параметры с `?`/`…`, `Рус / Eng`) и генерирует
коммитируемый `src/lsp/generated/api-catalog.ts`; тест генерации в память сравнивает с
коммитом (drift) и сверяет имена с публичным API из `src/` (логика кандидатов
`check-api-docs.mjs`). `constructible` — из скана `registerType`.

**Почему**: справочник — уже поддерживаемый человеком источник истины с описаниями
(правило 9 `AGENTS.md`), а `check-api-docs` гарантирует покрытие кода; парсить его таблицы
надёжнее, чем пытаться вытащить сигнатуры/описания из JS-функций. Генерация в TS-модуль
снимает вопрос JSON-импорта в `tsc`/Vite и делает сервер самодостаточным.

**Альтернативы**: JSON-ассет в `dist` (нужен шаг копирования, риск потерять файл);
парсить `docs/reference.md` при старте сервера (файловая зависимость, хрупкость путей);
ручной JSON (дублирование — прямо запрещено FR-012); рефлексия stdlib в рантайме (сигнатуры
и описания отсутствуют в `GlobalContext`).

## D7. Семантические проверки: консервативные Warning

**Решение**: правила OSJS3001–3003 (см. `contracts/diagnostics.md`): неизвестный глобальный
вызов, арность известной функции/метода, неизвестный тип в `Новый`. Только при успешном
разборе; severity Warning; подавления для импортов и динамических конструкций.

**Почему**: BSL динамичен; Error на предположении ломал бы доверие. Warning даёт ценность
(опечатки в именах, забытые аргументы), не блокируя работу. Стилевые правила исключены
спекой.

**Альтернативы**: только синтаксис (отклонено владельцем); Error-уровень (слишком шумно);
полный анализ потока данных (не нужен в первой версии, высокий риск).

## D8. Вывод типа для `Член.`: минимальная эвристика

**Решение**: известный тип только из `Новый Тип`; из переменной, которой тип присвоен
**однократно** в области; из прямого вызова stdlib-функции с единственным типом возврата в
каталоге. Иначе — `unknown`, список членов не предлагается.

**Почему**: цель — не соврать; неполный completion лучше неверного. Полный вывод типов —
отдельная большая задача без требования в спеке.

**Альтернативы**: всегда предлагать «все члены всех типов» (шум); не предлагать члены
вообще (нарушает FR-008: «когда тип однозначно определим»).

## D9. Грамматика: вендоринг MIT-грамматики `1c-syntax`

**Решение**: вендорить `1c-syntax/vsc-language-1c-bsl`, файл `syntaxes/1c.tmLanguage.json`,
зафиксированный коммит `c93f87c76d8a536a494039e9dc78a684b14b4e4c` (Copyright © 2015
xDrivenDevelopment, **MIT**); канонический source-of-truth — `1c-syntax/1c-syntax`
(`1c.YAML-tmLanguage`), но берём сгенерированный JSON, чтобы не вводить YAML→JSON шаг
сборки. Копия — `editors/osjs/osjs.tmLanguage.json` + `NOTICE.md` (копирайт, текст MIT,
URL/коммит, список правок).

**Обязательные правки** (проверены на реальной грамматике, полный список — в
`contracts/language-artifacts.md`):
1. `scopeName: source.osjs`, `name/displayName: osjs`, `fileTypes: ["osjs"]` — в upstream
   `["bsl","os"]`, это прямое нарушение FR-001/SC-002; `uuid` убрать.
2. Все суффиксы scope `.bsl` → `.osjs` (~40 имён).
3. Диалект: `Асинх|Async` → `storage.modifier.async.osjs`; `Ждать|Await` →
   `keyword.operator.word.await.osjs`; паттерны — до `meta.var-single-variable`, с границами
   слова (контекстные ложные срабатывания `Ждать(Х)` допустимы).
4. Добавить `Перейти/Goto`, `Выполнить/Execute`, `ДобавитьОбработчик/AddHandler`,
   `УдалитьОбработчик/RemoveHandler` — их нет в upstream, остальные `KW_*` покрыты.
5. Убрать SDBL: `include: "#query"` и вложенный comment-паттерн в строках.
6. Убрать неподдерживаемые директивы (`#Вставка`, `#Удаление`, `#native`, `#stack`) и
   спец-аннотации платформы (общий `&Имя` остаётся).
7. Удалить `support.*` (29 платформенных имён: `Справочники`, `НачатьТранзакцию`,
   `ПоказатьВопрос`, `XMLСтрока`; `Сообщить` там нет). Имена stdlib — зона semantic tokens
   (FR-010/FR-012), ручной список запрещён.
Питфоллы: `//`-паттерн раньше строкового; BOM в JSON снять до `parseRawGrammar`; `|`
обрабатывается string begin/end, отдельный паттерн не нужен.

**Почему**: 013 уже зафиксировала этот выбор; грамматика — 525 строк регэкспов, писать с
нуля дорого и рискованно; MIT позволяет использовать с указанием авторства; JSON-копия
избавляет от сборочного шага.

**Альтернативы**: писать с нуля (дорого); tree-sitter (второй анализатор, запрещён
FR-015); оставить upstream verbatim (ложная подсветка платформенных имён и `.os`);
брать YAML-source-of-truth (лишний билд-шаг).

## D10. Артефакты языка — `editors/osjs/`

**Решение**: `osjs.tmLanguage.json`, `language-configuration.json`, `languages.json`
(+ `scopeName`), `NOTICE.md` в `editors/osjs/`; стабильные пути; `languages.json` — минимум
метаданных. Фикстуры грамматики — `tests/fixtures/osjs/grammar.osjs` (не `fixtures/lsp`:
грамматика не про LSP), LSP-фикстуры — отдельно в `tests/fixtures/lsp/`.

**Почему**: артефакты общие для редакторов, а не часть Node-сборки; отдельный каталог
подчёркивает, что это поставка языка; сам upstream `1c-syntax` держит отдельные репозитории
под каждую редакторскую экосистему — «один каталог + JSON, остальное адаптеры» и есть
наша конвенция. Строго переносимы грамматика + `languages.json`; `language-configuration.json`
— де-факто VS Code-формат (VS Code и форки, Theia), у Neovim/Sublime/Zed/Helix свои форматы.

**Альтернативы**: держать внутри `src/lsp` (смешение слоёв); генерировать из upstream при
сборке (сетевая/сабмодульная зависимость; вендоренная копия с NOTICE надёжнее);
обещать «любой редактор» для конфигурации (неправда — нужны адаптеры).

## D11. Сборка и скрипты

**Решение**: `vite.lsp.config.ts` по образцу `vite.cli.config.ts`:
- `resolve.conditions: ['node']` (обязательно для subpath `vscode-languageserver/node`);
- `build.lib = { entry: src/node/lsp-server.ts, formats: ['es'], fileName: () => 'server.mjs' }`,
  `outDir: 'dist/lsp'`, `emptyOutDir: true`, `target: 'node20'`, `sourcemap: true`;
- `external: [/^node:/, ...builtinModules]` (иначе builtins подменяются browser-заглушками);
- `package.json`: `build:lsp`, `build:catalog`, `lsp` (`node dist/lsp/server.mjs`); в
  агрегатном `build` — **после** browser (browser-сборка с `emptyOutDir: true` чистит
  `dist/`, иначе снесёт `dist/lsp` и `dist/cli.mjs` — там уже так);
- `tsconfig.build.json`: `src/lsp` в `exclude` (иначе `tsc -p tsconfig.build.json` нашлёт
  `dist/node/lsp/*.d.ts` — типы инструментов не входят в публикуемый Node-пакет);
- `tsconfig.json`: `vite.lsp.config.ts` в `include` (прецедент: `vite.cli.config.ts` там
  отсутствует — это заодно исправляется);
- `files: ["dist"]` уже покрывает артефакт; `exports` не трогаем;
- точка входа `src/node/lsp-server.ts` — 5 строк: `createConnection(ProposedFeatures.all,
  process.stdin, process.stdout)` → `registerHandlers(connection)`; флаг `--stdio` не
  обязателен (стримы передаются явно).

**Почему**: минимальное повторение существующего паттерна CLI; браузерная сборка и
публичное API не меняются; drift-тест каталога входит в `pnpm test`.

**Альтернативы**: отдельный tsc-билд сервера (не нужен — Vite уже используется);
webpack/tsup (новая зависимость); отдавать сервер как `src`-файлы (нельзя запускать без
сборки); external вместо бандла (см. D1).

## D12. Тестирование

**Решение**: три уровня.
1. Юнит (Vitest, node env): провайдеры напрямую (чистые функции `text → diagnostics/
   completion/hover/tokens/symbols`) — основной объём; толерантные лексер/парсер/
   препроцессор; каталог; правила диагностики.
2. In-process протокол (проверено на реальном SDK): `PassThrough` +
   `createConnection(ProposedFeatures.all, toServer, toClient)` (server) +
   `createMessageConnection(StreamMessageReader/Writer)` (client) из `vscode-jsonrpc/node`;
   сценарии: `initialize` → `didOpen` (3 ошибки) → `publishDiagnostics` (3, верные
   range/version) → `didChange` → пустой набор; чужой languageId; запрос до `initialize`.
   Для этого `src/lsp/server.ts` экспортирует `registerHandlers(connection)` без
   side effects — тест переиспользует боевую регистрацию.
3. Smoke реального процесса: `spawn(process.execPath, ['dist/lsp/server.mjs'])`,
   `initialize` → `completion` → `shutdown`/`exit` (код 0); `describe.skipIf(!existsSync(dist))`,
   чтобы `pnpm test` не требовал сборки; прецедент spawn — `tests/http-node.test.ts`.
4. Грамматика: `vscode-textmate@^9.3.2` + `vscode-oniguruma@^2.0.1` (WASM, без нативных
   бинарников) на фикстуре `tests/fixtures/osjs/grammar.osjs`; хелпер
   `tests/helpers/textmate.ts` — импорт **только default** (CJS без `exports`: named-import
   падает в Node ESM), `onig.wasm` через `createRequire(...).resolve(...)`, `loadWASM`.
   Ассерты: таблица `{line, column, scope}`, инварианты `scopeName`/`fileTypes`/
   отсутствие `.os`/`.bsl`, нет висячих includes, обязательные поля конфигурации,
   `wordPattern` матчит `Сообщить`; анти-drift: наборы `KW_*`/`DIR_*` из единого
   `src/parser/keywords.ts` → keyword-scope.
   Проверено в Node 24.22; внутри именно Vitest — первый прогон обязателен.

**Почему**: быстрый feedback в Vitest + один реальный процесс для проверки сборки;
без VS Code/Playwright.

**Альтернативы**: `@vscode/test-electron` (тяжёлый, требует VS Code, не нужен без клиента);
`vscode-tmgrammar-test` (CLI-раннер вместо API, хуже встраивается в Vitest); спавнить TS
напрямую через `node --experimental-strip-types` (Node ≥20 не умеет — отклонено); собирать
Vite внутри теста (~0,3 с — лишняя сложность).

## D13. Сообщения и коды

**Решение**: сообщения на русском (язык проекта), `source: 'osjs'`, коды `OSJS1xxx`/`2xxx`/
`3xxx` по семействам; тексты-шаблоны стабильны и проверяются по коду+диапазону, а не по
полной строке (кроме якорных тестов).

**Почему**: консистентно с документацией и диагностиками движка; стабильные коды упрощают
тесты и будущие quick fixes.

**Альтернативы**: английские сообщения (нет локализации в первой версии); только текст без
кодов (хрупкие тесты).

## D14. Границы: один документ, без workspace-функций

**Решение**: сервер не реализует workspace-папки, переименование, форматирование,
foldingRange, диагностику по всему проекту. `definition` для `#Использовать` возвращает
`Location` целевого файла: чистый провайдер в `src/lsp` вычисляет путь и получает
**инжектированный** `resolveImport(importPath, documentUri) → fileUri | null` из
`src/node` (сам `src/lsp` файлы не читает и `node:path`/`node:url` не импортирует); для
untitled-документа — `null`.

**Почему**: минимальный полезный сервер; всё перечисленное не требуется спекой (Out of
Scope). Резолв импорта нужен только для навигации, без чтения содержимого.

**Альтернативы**: workspace-анализ (выходит за объём, требует индексации); чтение
импортированных файлов для проверки экспортов (отложено, потенциальные ложные
срабатывания); резолв URI внутри `src/lsp` (протащит Node-зависимости в слой провайдеров).

## D15. Производительность и сериализация анализа

**Решение**: анализ синхронный, по одному документу; кэш `Analysis` по версии;
`didChange` инвалидирует; на запросы, пока анализ не готов, отвечаем по последнему
завершённому. Лимит 200 диагностик и 10 000 строк для semantic tokens.

**Почему**: полный репарс укладывается в бюджет; асинхронная очередь усложняет порядок
ответов без выигрыша на одном файле, а синхронная публикация снимает гонки версий (D2).

**Альтернативы**: воркер-поток для анализа (не нужен при ~1,7 мс/1000 строк, добавляет
сложность); инкрементальный анализ (см. D3).

## D16. Semantic tokens: только стандартная легенда

**Решение**: легенда состоит только из стандартных token types LSP: `keyword`, `operator`,
`number`, `string`, `comment`, `decorator`, `function`, `method`, `variable`, `parameter`,
`property`, `enumMember`; `tokenModifiers: []`. Маппинг наших классов: директива →
`keyword` (или `macro`, если клиент его объявил), дата → `number`, аннотация → `decorator`,
имя метода → `method`, имя функции → `function`. Кастомные типы (`directive`, `date`) **не
используются**: клиент рендерит только типы, для которых у него есть правила.

**Почему**: переносимость между клиентами; semantic tokens — уточнение поверх грамматики,
а не способ ввести новые категории. 5 ints/token, сортировка по позиции, без пересечений,
многострочные литералы режутся по строкам (работает и при `multilineTokenSupport: false`);
`resultId`/delta не нужны, пока нет `range`/`delta` режимов.

**Альтернативы**: кастомные типы в легенде — не рендерятся в большинстве клиентов;
`tokenModifiers` для `Асинх`-методов — отложено (не требуется спекой).

## D17. Фолдинг: маркеры директив, тела — отступы, `foldingRange` вне объёма

**Решение**: `language-configuration.json` содержит одну пару `folding.markers` с
альтернацией `#Область|#Region|#Если|#If` ↔ `#КонецОбласти|#EndRegion|#КонецЕсли|#EndIf`.
Тела процедур/функций грамматикой не складываются (upstream скоупит только подпись);
их складывает indentation-folding редактора. LSP `foldingRange` не реализуется
(Out of Scope спеки).

**Почему**: одна пара — ограничение формата `folding.markers`; объединение альтернацией
даёт обе директивы без второго провайдера. Обещать фолдинг тел без LSP нельзя — это
поведение редактора, а не нашего артефакта; спека (FR-003) переформулирована честно.

**Альтернативы**: отдельный `foldingRange`-провайдер (расширение объёма, но не требуется);
пары для тел методов (ненадёжно, ломает вложенность); ничего не объявлять (FR-003 не
выполнен).
