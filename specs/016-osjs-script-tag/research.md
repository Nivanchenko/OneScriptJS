# Research: каноническая форма встраивания `<script type="text/osjs">`

Решения приняты владельцем и кларифицированы; здесь — технические следствия.

## D1. Форма и MIME

**Решение**: `<script type="text/osjs">` — единственная форма; `type` сравнивается ASCII
case-insensitively; `<one-script>` удаляется. `text/osjs` окончателен, параметры MIME не
поддерживаются.

**Почему**: raw text по стандарту HTML — корректная семантика для языка с `<`/`&`;
нативно скрыт; data blocks — стандартный механизм (JSON-LD, import maps, x-templates).

**Альтернативы**: custom element (HTML-парсинг содержимого → экранирование); оба сразу
(лишняя поверхность при отсутствии пользователей).

## D2. Момент запуска

**Решение**: если `document.readyState !== 'loading'` — `runAll()` сразу при инициализации
модуля; иначе — один раз на `DOMContentLoaded`. Повторный запуск запрещён флагом.

**Почему**: работает при любом размещении тега и `defer`/`async`; детерминированно.

**Альтернативы**: только `DOMContentLoaded` (поздняя загрузка бандла не исполняет блоки);
сразу без ожидания DOM (код может работать до готовности страницы).

## D3. Порядок и изоляция

**Решение**: блоки собираются в порядке документа и исполняются **последовательно**
(`for … await executeBlock`), а не параллельно; каждый — в свежем `createBrowserGlobalContext()`;
ошибка ловится внутри блока (`console.error`) и не прерывает остальные.

**Почему**: `preloadModuleSources` асинхронен; без сериализации порядок выполнения мог бы
нарушиться (spec FR-003). Изоляция соответствует текущей модели (ранама — контекст на
элемент).

**Альтернативы**: параллельный запуск (порядок не гарантирован); один общий контекст
(ломает изоляцию и миграцию).

## D4. Контексты `id` / `data-os-*`

**Решение**: сохранить текущую семантику `registerScriptContext(id || null, ctx)`: блок с
`id` регистрирует контекст; первый блок без `id` становится контекстом по умолчанию для
`data-os-*` без `data-os-script`; остальные без-id блоки изолированы и не выбираются;
дубликат `id` — «последний побеждает». `src/browser/dom-events.ts` не меняется.

**Почему**: минимизирует миграцию, сохраняет существующие примеры/тесты.

## D5. Удаление `<one-script>` без deprecated-режима

**Решение**: класс `OneScriptElement`, `customElements.define`, `injectHiddenStyle` и все
упоминания удаляются; элемент в DOM больше не скрывается нашим CSS и не исполняется.

**Почему**: пользователей нет; две формы навсегда = двойные доки/тесты/инструменты.

## D6. Миграция тестов

**Решение**: хелперы `render()` в браузерных тестах создают `script[type="text/osjs"]`
с `textContent` **до** импорта `src/browser/onescript`, затем импортируют модуль; где нужно
— эмитят `DOMContentLoaded`. Добавляется `tests/browser-script-tag.test.ts` с семантикой
(порядок, изоляция, raw-text, `id`, ошибки, отсутствие `<one-script>`).

**Почему**: на happy-dom `readyState` обычно уже `complete`, поэтому блоки должны быть в
DOM к моменту инициализации модуля; это же проверяет ветку «DOM уже готов».

**Альтернативы**: эмуляция `readyState`/событий в каждом тесте (хрупко); запуск через
MutationObserver (вне v1).

## D7. Диагностика опасных последовательностей

**Решение**: контракт в `contracts/`; реализация — в embedded-спеке 015. `OSJS4001`
(Error) — `</script>` в BSL-коде; `OSJS4002` (Warning) — `<script`/`<!--` в BSL-строках.
Runtime при обрыве просто получает обрезанный `textContent` и сообщает ошибку разбора в
`console.error`.

**Почему**: рантайм не может отличить обрыв от конца кода; линтер видит HTML целиком и
может подсказать.

## D8. Миграция примеров/доков

**Решение**: механическая замена тегов в `examples/*.html`; README/AGENTS/architecture/
status/task.md — текстовая миграция; спеки 013/014/015 — пометки «было `<one-script>`,
заменено 016». Конституция — поправка принципа II, MAJOR 3.0.0, Sync Impact Report.

**Почему**: конституция — часть definition of done; статус не должен врать.

## D9. Без новых зависимостей и без изменений ядра

**Решение**: только `src/browser/onescript.ts` (+ комментарий в `dom-events.ts`); ядро,
`src/node`, CLI, `.osjs`-формат не меняются. happy-dom уже установлен.

**Альтернативы**: HTML-парсер для рантайма (не нужен — DOM уже даёт блоки); новые
зависимости (запрещено конституцией без обоснования).

## D10. CSP и совместимость

**Решение**: поведение не ослабляется; data blocks не исполняются браузером. CSP-проверка —
задача реализации: при блокировке inline-data-blocks политикой задокументировать требование
(и предусмотреть nonce/hash-совет), не меняя модель безопасности. happy-dom и HTML-грамматика
VS Code (override `source.js` для `text/osjs`) проверяются в реализации/015.
