# Feature Specification: Каноническая форма встраивания — `<script type="text/osjs">`

**Feature Branch**: `feat/linter`

**Created**: 2026-11-12

**Status**: Implemented (runtime + тесты + миграция; правила OSJS4001/4002 — контракт, реализация в спеке 015)

**Input**: Решение владельца проекта после оценки двух форм встраивания: «выбираю
`text/osjs`; проблемы с `</script>` можно зашить в линтер, чтобы он в диагностиках светил
это как ошибку». Пользователей у продукта нет, обратная совместимость не требуется —
можно задизайнить каноническую форму заново.

## Context

Сейчас браузерный вход OneScriptJS исполняет BSL из кастомного элемента `<one-script>`.
Оценка показала, что это тупиковая форма: содержимое custom element парсится **как HTML**,
поэтому язык с `<`, `>`, `&` требует «налога на экранирование» (`Если А<Б`, `&copy;`,
`</div>` в строках), может пострадать от HTML-форматтеров, а до загрузки движка код
потенциально виден (нужен инжектируемый CSS `one-script { display: none }`).

Решение: **каноническая форма — `<script type="text/osjs">`**, HTML data block. Браузер не
исполняет такой скрипт, а его содержимое по стандарту HTML — **raw text**: `<`, `>`, `&`
остаются символами BSL, разметка не интерпретируется, элемент нативно скрыт и не
попадает в извлечение текста. Это тот же механизм, что `application/ld+json`, import maps
и `text/x-template`.

Единственная плата — последовательность `</script>` внутри кода обрывает блок (законный
конец raw-text элемента). Это осознанный компромисс: он уже, чем HTML-мины custom element,
и закрывается **обязательной диагностикой линтера** (Error), которая объясняет обрыв и
подсказывает обход (конкатенация строк).

Спека 014 (редакторные инструменты) реализована и от формы встраивания не зависит; спека
015 (встроенный `.osjs` в HTML) переписывается под `<script type="text/osjs">` и получает
эту диагностику как правило.

`<one-script>` как форма встраивания **не поддерживается**: элемент не регистрируется,
примеры/тесты/документация переводятся на новую форму; отказ фиксируется в README,
`docs/status.md` и поправке конституции (принцип II — браузерный контракт).

## Clarifications

### Session 2026-11-12

- Q: Поддерживать ли в v1 загрузку внешних `.osjs`-файлов через `<script type="text/osjs" src="app.osjs">`, или ограничиться inline-кодом? → A: Только inline в v1; атрибут `src` зарезервирован и в v1 игнорируется.
- Q: Должен ли движок исполнять блоки, добавленные в DOM после загрузки страницы? → A: Только статические блоки в v1; динамика — через JS-API движка (`run`/`runScript`), MutationObserver — отдельное будущее решение.
- Q: Как линтер реагирует на `<script`/`<!--` внутри BSL-кода (кроме Error для `</script>`)? → A: `</script>` — Error, `<script`/`<!--` — Warning.
- Q: Когда исполнять статические блоки, если движок загружен позже готовности DOM (`defer`/`async`)? → A: Сразу при инициализации, если `document.readyState !== 'loading'`; иначе на `DOMContentLoaded`.
- Q: Какой контекст получают `data-os-*`-обработчики, если у блока нет `id`? → A: Сохранить текущую семантику: первый блок без `id` — контекст по умолчанию; остальные без-id блоки изолированы; дубликат `id` — «последний побеждает».

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Страница исполняет BSL из `<script type="text/osjs">` (Priority: P1)

Разработчик подключает движок в браузере и кладёт код в теги
`<script type="text/osjs">…</script>`. При загрузке страницы код исполняется: `Сообщить`
выводит в консоль, DOM/события/HTTP/фоновые задания доступны как раньше. Код в тегах не
отображается на странице и не исполняется браузером как JavaScript. Несколько блоков на
странице выполняются в порядке документа.

**Why this priority**: Это базовый runtime-контракт; без него новая форма не существует.

**Independent Test**: страница с двумя блоками (второй зависит от порядка/побочного
эффекта) в браузере/happy-dom: вывод в консоль соответствует порядку документа; блоки не
видны в отрендеренном тексте; JS-ошибок «нашего» кода нет.

**Acceptance Scenarios**:

1. **Given** страница с `<script type="text/osjs">Сообщить("привет");</script>`, **When**
   она открыта в браузере с подключённым движком, **Then** в консоли `привет`, блок не
   отображается и не исполняется как JS.
2. **Given** два блока, второй печатает после первого, **When** страница открыта, **Then**
   порядок выполнения совпадает с порядком документа.
3. **Given** блок с `#Использовать "lib/Модуль.osjs"`, **When** страница открыта, **Then**
   импорт разрешается относительно `document.baseURI` и работает так же, как раньше.
4. **Given** страница без блоков `text/osjs`, **When** движок загружен, **Then** он ничего
   не исполняет и не добавляет глобальных побочных эффектов.

---

### User Story 2 - Авторство без HTML-экранирования; `</script>` подсвечивается (Priority: P2)

Разработчик пишет обычный BSL: `Если А<Б`, `Или`, строки с `&`, `</div>` и HTML-фрагментами
работают без экранирования и без пробелов вокруг `<`. Если в строке/комментарии всё же
встречается последовательность `</script>`, линтер показывает **ошибку** с объяснением, что
она обрывает блок, и подсказкой, как писать (конкатенация строк).

**Why this priority**: Снимает главную причину выбора формы и закрывает единственную мину
raw text; без этого автор может молча получить обрезанный код.

**Independent Test**: страница, где BSL содержит `<`, `&`, `</div>` в строке — значение при
исполнении совпадает с ожидаемым. Отдельная фикстура с `"</script>"` в строке: в редакторе
(embedded-режим 015) публикуется Error-диагностика с правильным диапазоном и текстом.

**Acceptance Scenarios**:

1. **Given** код `Если А<Б Тогда …` (без пробелов), **When** страница открыта, **Then**
   сравнение вычисляется как BSL-выражение.
2. **Given** строка `"Tom & Jerry"` и `"<div>&copy;</div>"`, **When** код исполняется,
   **Then** значения содержат ровно эти символы (entity не декодируются).
3. **Given** блок, где в BSL-строке есть `</script>`, **When** HTML открыт в редакторе с
   нашими инструментами, **Then** публикуется ошибка (например, `OSJS4001`) с диапазоном
   на месте обрыва и текстом-подсказкой; код считается ошибочным, а не молча обрезанным.
4. **Given** `<!-- <script type="text/osjs">…</script> -->` в HTML-комментарии, **When**
   страница открыта, **Then** содержимое не исполняется и не считается блоком.

---

### User Story 3 - Контексты, изоляция и декларативные обработчики (Priority: P3)

Каждый блок — отдельный контекст исполнения (как сейчас у элементов): переменные и методы
одного блока не видны в другом; `id` блока регистрирует контекст для `data-os-*`-обработчиков
(поиск по `data-os-script`), ошибка в одном блоке не останавливает остальные. Динамически
добавленные после загрузки блоки в первой версии не исполняются.

**Why this priority**: Сохраняет существующую модель исполнения и предсказуемость; меняется
только форма носителя кода.

**Independent Test**: страница с двумя блоками и обработчиками `data-os-*`: изоляция
символов, привязка по `id`, падение одного блока не мешает второму, лог ошибки в консоль.

**Acceptance Scenarios**:

1. **Given** два блока с одинаковыми именами переменных, **When** оба исполнены, **Then**
   значения не пересекаются.
2. **Given** блок `id="app"` и кнопка с `data-os-click` + `data-os-script="app"`, **When**
   пользователь кликает, **Then** обработчик исполняется в контексте этого блока.
3. **Given** первый блок бросает исключение, **When** страница загружена, **Then** второй
   блок всё равно исполняется, а ошибка попадает в `console.error`.
4. **Given** блок, вставленный в DOM после загрузки страницы, **When** он появляется,
   **Then** он не исполняется (v1; отложенное поведение зафиксировано).

---

### User Story 4 - Старая форма удалена, экосистема переведена (Priority: P4)

`<one-script>` больше не поддерживается и нигде не заявляется: элемент не регистрируется,
скрывающий CSS не инжектируется, примеры, тесты, README, документация и спеки используют
`<script type="text/osjs">`. В исходном ТЗ зафиксирована поправка: контракт встраивания
пересмотрен осознанно (пользователей нет).

**Why this priority**: Без чистого удаления останутся две формы, противоречивые доки и
двойная поддержка в редакторных инструментах.

**Independent Test**: `grep -R "<one-script"` по отслеживаемым файлам не находит вхождений
(кроме исторического упоминания в решении/ТЗ); браузерные тесты и примеры используют новую
форму и зелёные; old-look элемент не регистрируется.

**Acceptance Scenarios**:

1. **Given** страница с `<one-script>…</one-script>`, **When** открыта, **Then** код не
   исполняется, элемент не скрывается нашим CSS, в консоли нет «наших» ошибок о нём.
2. **Given** репозиторий после миграции, **When** выполняется поиск по tracked-файлам,
   **Then** `<one-script>` встречается только в исторических/решенческих упоминаниях.
3. **Given** `examples/*.html`, **When** они открыты, **Then** все исполняемые примеры
   работают на новой форме.
4. **Given** README/AGENTS/конституция, **When** читаются, **Then** браузерный контракт
   описан как `<script type="text/osjs">`.

---

### Edge Cases

- **`</script>` в BSL-строке/комментарии** — обрыв блока; линтер (015) даёт Error с
  объяснением и подсказкой; runtime исполняет обрезанный текст → ошибка разбора в
  `console.error` (не молчаливый успех). Документированный обход: `"</" + "script>"` или
  вынести HTML-шаблон из BSL-строки.
- **`<script` внутри BSL-строки** — последовательность `<script` в script-data может менять
  legacy-состояния HTML-парсера; на практике редко (HTML в строках), документируется вместе
  с `</script>`; линтер может предупреждать отдельным кодом (опционально).
- **`<!--` в начале блока/строки** — legacy script-data escaped state; линтер может
  предупреждать; рекомендованный гайдлайн — не начинать код с `<!--`.
- **`type` отсутствует/другой** (`text/javascript`, `module`, пусто) — не наш блок, не
  исполняется; `type` сравнивается ASCII case-insensitively.
- **`type="text/osjs"` с `src`** — в v1 не поддерживается (атрибут игнорируется), зарезервировано.
- **Незакрытый тег** до EOF — содержимое до конца документа считается блоком; ошибку HTML
  сообщает HTML-валидатор, не мы.
- **Несколько блоков / пустой блок / блок в `<head>`** — поддерживаются; пустой блок — no-op.
- **Порядок и DOM**: движок ждёт готовности DOM (`DOMContentLoaded`/`readyState`), затем
  исполняет все блоки в порядке документа; блоки, вставленные динамически, в v1 не
  исполняются.
- **CRLF/кодировка**: script-контент приходит с нормализованными переводами строк (HTML
  парсер); позиции/значения многострочных строк `|` обрабатываются как в движке.
- **CSP**: data block не исполняется браузером; поведение под строгим `script-src`
  проверить (inline-script-политика не должна блокировать неисполняемые data blocks).
- **Дубликат `id`** — последний зарегистрированный контекст побеждает (как и раньше);
  документируется.
- **Ошибка в одном блоке** — остальные исполняются; ошибка в `console.error`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Движок ДОЛЖЕН исполнять BSL только из `script[type="text/osjs"]`
  (значение `type` сравнивается без учёта регистра); другие `type`/элементы не исполняются.
- **FR-002**: `<one-script>` ДОЛЖЕН быть удалён как форма встраивания: custom element не
  регистрируется, скрывающий CSS не инжектируется, поддержка не заявляется. `.osjs`-файлы,
  CLI и Node-API не меняются.
- **FR-003**: Блоки ДОЛЖНЫ собираться и исполняться в порядке документа: если
  `document.readyState !== 'loading'` — сразу при инициализации движка (поздняя загрузка
  через `defer`/`async` допустима), иначе — на `DOMContentLoaded`. Каждый блок — в своём
  контексте; ошибка одного блока не останавливает остальные (ошибка → `console.error`).
- **FR-004**: `id` блока ДОЛЖЕН регистрировать его контекст для декларативных обработчиков
  (`data-os-*`, поиск по `data-os-script`). Сохраняется текущая семантика: первый блок без
  `id` становится контекстом по умолчанию для обработчиков без `data-os-script`; остальные
  блоки без `id` исполняются изолированно и для обработчиков не выбираются; дубликат `id` —
  «последний побеждает».
- **FR-005**: `#Использовать` ДОЛЖЕН разрешаться относительно `document.baseURI` (как
  сейчас); кеш/циклы — без изменений.
- **FR-006**: Браузерный бандл не должен требовать CSS-скрытия блоков: `script[type="text/osjs"]`
  нативно не отображается; инжекция `one-script { display:none }` удаляется.
- **FR-007**: Инструменты (embedded-режим спеки 015) ДОЛЖНЫ диагностировать
  последовательность `</script>` в BSL-коде как **Error** со стабильным кодом (предложение:
  `OSJS4001`), диапазоном на месте обрыва и текстом-подсказкой (обрыв блока; как писать
  безопасно). Последовательности `<script` и `<!--` в BSL-строках ДОЛЖНЫ выдаваться
  **Warning** (тот же диагностический семейный код/`OSJS4002`): они редко, но меняют
  legacy-состояния script-data; не блокируют работу.
- **FR-008**: Явно ДОКУМЕНТИРОВАТЬ последствия `</script>` (Error), `<script`/`<!--`
  (Warning) в BSL-строках:
  что происходит (обрыв/нестандартный разбор), как писать безопасно и что runtime-ошибка
  при обрыве попадает в `console.error`, а не проглатывается.
- **FR-009**: Динамически добавленные после загрузки блоки в v1 НЕ исполняются (нет
  MutationObserver); для динамического исполнения используется JS-API движка
  (`run`/`runScript`). Поведение документируется, автозапуск динамических блоков —
  отдельное будущее решение.
- **FR-010**: Атрибут `src` у `text/osjs` в v1 НЕ поддерживается (игнорируется);
  зарезервирован для будущего (внешний `.osjs`-файл).
- **FR-011**: Примеры (`examples/*.html`), браузерные тесты, README, `docs/status.md`,
  `docs/architecture.md`, AGENTS и спеки 013/014/015 ДОЛЖНЫ быть переведены на новую форму;
  исходное ТЗ (`task.md`) получает пометку о пересмотре контракта (решение владельца).
- **FR-012**: Браузерные тесты ДОЛЖНЫ покрывать: исполнение и порядок блоков, raw-text
  семантику (`<`, `&`, `</div>`), `data-os-*` по `id`, изоляцию блоков, падение одного
  блока, отсутствие регистрации `<one-script>`, отсутствие `one-script`-CSS, импорты.
  Отдельные тесты — Error для `</script>` и Warning для `<script`/`<!--` (в слое 015) на
  HTML-фикстурах.
- **FR-013**: Конституция (принцип II: браузерный контракт `<one-script>`) ДОЛЖНА быть
  поправлена вместе с Sync Impact Report; изменение — MAJOR по governance (переопределение
  контракта), с явным одобрением владельца (получено).
- **FR-014**: Никаких новых зависимостей; размер браузерного бандла не растёт существенно;
  `dist/onescript.js` остаётся единым IIFE-бандлом.
- **FR-015**: Безопасность не ослабляется: data block не исполняется браузером, CSP-поведение
  не хуже текущего (проверить и зафиксировать); ошибки скриптов — в `console.error`.

### Key Entities

- **Data block** — `script[type="text/osjs"]` в документе: исходник BSL, позиция в документе,
  `id` (опционально), `type` (наш MIME).
- **Контекст исполнения блока** — свежий `GlobalContext` на блок; регистрируется по `id`
  для декларативных обработчиков.
- **Порядок исполнения** — документный порядок блоков; детерминирован.
- **Диагностика обрыва** — Error-правило (`OSJS4001`) в embedded-режиме 015: позиция обрыва,
  объяснение, подсказка.
- **Браузерный контракт** — «код исполняется из `<script type="text/osjs">`» (заменяет
  `<one-script>` в конституции/README/ТЗ).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Страница с двумя-тремя блоками исполняет их в порядке документа; ни один блок
  не отображается в тексте страницы и не исполняется как JS.
- **SC-002**: Код с `А<Б`, `>` и `&` в строках исполняется с BSL-семантикой без
  экранирования; значения строк совпадают посимвольно.
- **SC-003**: Несколько блоков изолированы (нет общих переменных), падение одного не мешает
  другим, ошибки — в `console.error`.
- **SC-004**: `data-os-*`-обработчики привязываются к контексту блока по `id`.
- **SC-005**: `#Использовать` из блока работает относительно `document.baseURI` (страница
  открыта из файла/локального сервера).
- **SC-006**: В HTML с `</script>` внутри BSL-строки embedded-линтер выдаёт Error с
  диапазоном и подсказкой; `<script`/`<!--` в строках дают Warning; без линтера runtime при
  обрыве даёт ошибку разбора в `console.error`, а не «тихий успех».
- **SC-007**: `<one-script>` не регистрируется и не исполняется; `grep` по tracked-файлам не
  находит его вне исторического упоминания решения.
- **SC-008**: Примеры, браузерные тесты, README, docs, AGENTS и спеки переведены; `pnpm
  typecheck && pnpm test && pnpm build` зелёные; `pnpm demo`/`examples/` работают на новой
  форме.
- **SC-009**: Конституция поправлена (принцип II + Sync Impact Report), версия обновлена.
- **SC-010**: Публичный Node-API и `.osjs`-исполнение не изменились; новых зависимостей нет.

## Out of Scope

- Реализация редакторных инструментов для встроенных блоков — спека 015 (она получает
  правило `OSJS4001` и сканер `<script type="text/osjs">`).
- `src`-атрибут (внешний `.osjs`), динамическая вставка блоков, MutationObserver.
- Модульная/ESM-семантика тегов script, source maps, `defer`/`async`-аналоги.
- Изменение `.osjs`-формата, CLI и Node-API.
- Поддержка `<one-script>` в любом виде (включая deprecated-режим) — решение владельца:
  пользователей нет, старая форма удаляется.
- Автоматическая миграция сторонних страниц.

## Assumptions

- **Пользователей нет**, обратная совместимость не требуется (решение владельца); удаление
  `<one-script>` допустимо и предпочтительно.
- **MIME `text/osjs`** — окончательный выбор; значение `type` сравнивается
  case-insensitively; параметры типа не поддерживаются.
- **Только inline-код в v1**: `src` у `text/osjs` не поддерживается и игнорируется
  (зарезервирован); внешние `.osjs`-файлы встраиваются через API движка или будущую версию.
- **Raw text по стандарту HTML** — источник семантики: `<`, `>`, `&` не интерпретируются;
  `</script` завершает блок. Это принимается как компромисс, компенсируемый линтером (015).
- **Диагностика `</script>`** реализуется в embedded-режиме 015 (там есть сканер HTML и
  LSP), а не в браузерном рантайме: рантайм видит уже обрезанный `textContent` и может лишь
  сообщить ошибку разбора.
- **Скрипт движка подключается как раньше** (`<script src="/onescript.js"></script>`), форма
  data block не конфликтует с ним; порядок загрузки/готовности DOM обеспечивает исполнение
  после разбора.
- **CSP**: неисполняемые data blocks не блокируются `script-src` (проверить при реализации);
  если это не так — документировать требование к политике.
- **happy-dom** в тестах достаточно точно воспроизводит script-data; при расхождениях
  добавить реальный браузерный тест (Playwright — спека 007).
- **`task.md` — исторический документ**: контракт пересматривается пометкой, а не
  переписыванием исходного ТЗ.
