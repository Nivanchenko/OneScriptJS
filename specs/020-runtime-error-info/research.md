# Research: семантика позиции/модуля/стека в ошибках

**Feature**: `specs/020-runtime-error-info` | **Date**: 2026-11-24

Источники: эталон `reference/OneScript` (C#), текущий движок (`src/`), `docs/reference.md`.
Эталон — способ сверки унаследованного BSL-подмножества (конституция I), а не граница
продукта; расхождения ниже осознанны и фиксируются тестами/`docs/status.md`.

## Решения

### R1. Снимок ошибки снимается в момент возникновения, один раз

- **Эталон**: `MachineInstance` ловит `ScriptException` и вызывает
  `exc.SetPositionIfEmpty(GetPositionInfo())` — позиция заполняется только если её ещё нет
  (`ScriptException.SetPositionIfEmpty`); обычные исключения оборачиваются в
  `ExternalSystemException` и тоже получают позицию (`MachineInstance.cs:480-522`).
- **Наше решение**: при выходе ошибки на границу BSL-оператора (`exec`/`eval` интерпретатора)
  вешаем `ErrorSnapshot`, если его ещё нет. Ошибки, созданные `ВызватьИсключение`, снимок уже
  имеют. Это ровно «set if empty»: первый (самый внутренний) снимок побеждает.
- **Следствие**: перевыброс не перезаписывает позицию; `Попытка` не портит снимок.

### R2. Позиция: модуль, строка, исходная строка

- **Эталон**: `НомерСтроки` = `LineNumber` (1-based; `-1` = вне текста), `ИмяМодуля` =
  `ScriptException.ModuleName` (для ошибки — `_module.Source.Name`), `ИсходнаяСтрока` =
  `Code` (строка исходника из `Source.GetCodeLine`). `ColumnNumber` есть в эталоне, но в
  `ИнформацияОбОшибке` не выводится — в наш объём не входит.
- **Наше решение**: `НомерСтроки` — `stmt.pos.line` (1-based), `ИсходнаяСтрока` — строка
  текста модуля по номеру, `ИмяМодуля` — идентификатор источника (таблица в
  `data-model.md`). Вне блока `Исключение` — пустая ошибка (`НомерСтроки` = 0).
- **Альтернатива**: хранить колонку — отклонено (в 1С-API её нет, в UI не просили).

### R3. Стек: порядок и состав

- **Эталон**: `_callStack` — `Stack<ExecutionFrame>`; `CreateFullCallstack()` перечисляет его
  LIFO, т.е. **текущий кадр первым** (`MachineInstance.cs:1331-1335`); кадр —
  `ExecutionFrameInfo { Source, LineNumber, MethodName }`, `Source = module.Source.Location`
  (`MachineInstance.cs:2599-2604`). `ПолучитьСтекВызовов()` отдаёт
  `КоллекцияКадровСтекаВызовов` с `Количество()`, индексацией и `Для Каждого`
  (`StackTraceCollectionContext.cs`), элементы — `КадрСтекаВызовов` (`Метод`,
  `НомерСтроки`, `ИмяМодуля`).
- **Наше решение**: снимок `FrameSnapshot[]` изнутри наружу; включаем кадры тела модуля
  (`<модуль>`), BSL-методов, конструкторов, обработчиков событий, динамических фрагментов
  (`<Выполнить>`/`<Вычислить>`). Не включаем stdlib/платформу и служебные обёртки.
- **Решение**: `ПолучитьСтекВызовов()` возвращает `КоллекцияКадровСтекаВызовов` — свой тип в
  `src/runtime` (не stdlib, чтобы не нарушать направление слоёв): `Количество()`, индексация
  0-based, `Для Каждого`. Для пустой ошибки — пустая коллекция (в эталоне `Неопределено`;
  расхождение фиксируется в `docs/status.md`).

### R4. Идентификаторы источников

- **Эталон**: `SourceCode.Name` по умолчанию = `ICodeSource.Location` (путь файла); для
  строковых источников — их location (`SourceCodeBuilder.cs:45-54`).
- **Наше решение** (детали — `data-model.md`): Node — путь, переданный в `run` (главный) и
  разрешённый путь (импорты/классы); stdin — `<stdin>`; браузер — URL файла, для inline-блока
  `<URL страницы>#<id>` или `#block<N>`; динамика — `<Выполнить>`/`<Вычислить>`;
  библиотека/тесты без пути — `<скрипт>`.
- **Почему не «имя файла без пути»**: в проекте уже есть пути/URL как идентичность (LSP,
  `ТекущийСценарий`), а коллизии имён модулей возможны.

### R5. Перевыброс

- **Эталон**: `ВызватьИсключение;` без аргумента бросает тот же `ScriptException`
  (`_currentFrame.LastException`) — позиция сохраняется. `ВызватьИсключение
  ИнформацияОбОшибке()` создаёт **новое** `ParametrizedRuntimeException` с `Причина` =
  переданный объект; позиция нового исключения пустая и заполняется на строке перевыброса
  (`MachineInstance.cs:1259-1300`).
- **Наше решение**: оба вида перевыброса **сохраняют исходный снимок** (позиция/стек
  возникновения); `ВызватьИсключение <новое значение>` даёт снимок строки перевыброса.
  Причина: `Причина`/вложенные причины — вне объёма (spec FR-005), а сохранение исходной
  позиции полезнее для диагностики.
- **Расхождение** с эталоном для формы с `ИнформацияОбОшибке` — осознанное, фиксируется
  тестом и `docs/status.md` (раздел «Известные пробелы»).

### R6. `ПодробноеОписаниеОшибки`

- **Эталон**: `ИнформацияОбОшибке.ПодробноеОписаниеОшибки()` = `ActualException().ToString()`
  — текст исключения с позицией/фрагментом кода и стеком CLR
  (`ExceptionInfoContext.cs:183-190`); это **метод**, а не свойство.
- **Наше решение**: метод `ПодробноеОписаниеОшибки()` возвращает `Описание` + BSL-стек в
  формате из `contracts/error-info-api.md`; свойство с тем же именем сохраняется как
  совместимость (сейчас оно есть и возвращает `Описание`). Формат фиксируется тестом.
- **Почему свойство сохраняем**: наш `docs/reference.md` уже документирует его как свойство;
  удаление — ломающее изменение без пользы.

### R7. Встроенные `КраткоеПредставлениеОшибки` / `ПодробноеПредставлениеОшибки`

- **Эталон**: `Краткое` = `Описание`; `Подробное` = `GetDetailedDescription()` = описание +
  «по причине:» для вложенных причин (стека BSL там нет) —
  `StandardGlobalContext.cs:110-120`, `ExceptionInfoContext.GetDetailedDescription`.
- **Наше решение**: **не меняем**. Вложенных причин у нас нет, поэтому оба возвращают
  `Описание`, как сейчас. Это соответствует эталону при отсутствии причин.

### R8. Async, `Ждать`, фоновые задания

- **Эталон**: async-рантайма нет (в C# OneScript async только разбирается); фоновые задания
  — отдельные потоки с `ИнформацияОбОшибке`.
- **Наше решение**: снимок создаётся в момент throw в том же генераторе; объект ошибки
  (со снимком) переносится через `Обещание`/`ФоновоеЗадание` без изменений. Необработанные
  ошибки `Обещаний` и ошибки заданий печатаются тем же форматом, что и синхронные.
- **Риск**: ошибка, пойманная в `Ждать` в другом кадре, сохраняет позицию возникновения (а не
  точку `Ждать`) — это ожидаемо и полезно.

### R9. Динамический код (`Выполнить`/`Вычислить`)

- **Эталон**: компилируется отдельным модулем (`EvalCompiler`), у него своя позиция.
- **Наше решение**: идентификатор `<Выполнить>`/`<Вычислить>`, строка — внутри фрагмента
  (1-based), в стеке — кадр вызывающего кода. `ИсходнаяСтрока` — строка фрагмента.

### R10. Синхронный быстрый путь и производительность

- **Решение**: кадры — push/pop на вызовах; `exec` обновляет строку текущего кадра (запись
  числа); снимок — только при ошибке. Новых `yield`, `await` и асинхронности нет; поведение
  синхронного скрипта не меняется (проверяется существующими тестами async/sync).
- **Альтернатива**: хранить позицию в каждом AST-узле/инструкции — не нужно, `stmt.pos` уже
  есть.

### R11. Где именно ставится снимок

- **Решение**: на границе `exec` (оператор) и `execDynamic` (динамический фрагмент). Для
  ошибок из `eval` (выражения) снимок ставится на ближайшем объемлющем `exec` — позиция
  оператора. Это совпадает с эталоном (позиция инструкции/строки в момент исключения).
- **Почему не в `eval`**: позиция выражения может быть внутри строки; пользователю нужен
  оператор (строка), а не подвыражение.

### R12. Ограничения хостового вывода (регрессы браузера/CLI)

- В `tests/browser-script-tag.test.ts` проверяются подстроки `console.error`:
  `Не удалось загрузить`, URL, `HTTP 404`, подсказка про `</script>` (по регулярке
  `/строка \d+,\s*колонка/i` в `describeError`), а также `errors.length`. Новый формат
  ошибки BSL должен быть **аддитивным**: старые фрагменты и подсказка сохраняются.
- Ошибки загрузки/разбора блока не имеют снимка — печатаются как раньше.
- В CLI до фичи печатался только `message`; для ошибок без снимка сохраняем это поведение
  (деградация без падения).

### R13. Стек между модулями

- Импортированный модуль/класс исполняется в **отдельном** `Interpreter` (`modules.ts:157,205`),
  поэтому стек «per-Interpreter» не соберёт цепочку вызовов между модулями.
- **Решение**: при вызове метода другого модуля передавать снимок кадров вызывающего
  (`parentFrames`) — либо необязательным аргументом `BslObject.callMethod`, либо через
  текущий контекст вызова в env. Итоговый стек = кадры целевого интерпретатора + parentFrames.
- `forkForJob` создаёт отдельный `Interpreter` — у задания свой стек (без parentFrames
  главного потока); это соответствует модели «поток задания».

### R14. Стек на invocation, а не на интерпретатор (async)

- При async-вызовах на одном `Interpreter` может быть несколько приостановленных
  invocation-ов; единый мутабельный `frames` смешает их стеки.
- **Решение**: стек принадлежит invocation-у (root `drive`): либо прокидывается параметром
  через `exec`/`eval`/`callMethod`/`invoke*`, либо сохраняется/восстанавливается на каждом
  root с осознанным ограничением. Для MVP обязателен как минимум корректный стек для
  одного async-метода + кадра вызывающего; при двух конкурентных async-вызовах стек не
  должен «склеиваться» — если это дорого, фиксируется `shortcut:` и тестом.

### R15. Аннотируются только `Error`

- Сигналы управления (`ReturnSignal`/`BreakSignal`/`ContinueSignal`/`GotoSignal`) — не `Error`
  и снимка не получают; `execTryExcept` уже фильтрует `instanceof Error`.
- Снимок ставится только если его ещё нет (first throw wins) — повторная аннотация запрещена.

### R16. Текст-контракты, которые нельзя ломать

- 19+ точных `toEqual` на `ОписаниеОшибки()`/`Описание` (в т.ч. `Поле объекта не обнаружено:
  'Несуществующее'`, `Неизвестный символ: …`, `текст ошибки`); 2 подстрочных `Найти(...)`.
- `ФоновоеЗадание.ИнформацияОбОшибке.Описание` — пользовательский текст (3 теста).
- `toThrow("...")` — подстрока, префикс не ломает; `toThrow(/.../)` — сохранять подстроки.
- Синхронный `run()` без ошибок остаётся синхронным (не Promise).

### R17. Подтверждения и уточнения по эталону (сверка по исходникам C#)

- `НомерСтроки` — 1-based, **строка возникновения**; `SetPositionIfEmpty` — «first throw wins».
  `ВызватьИсключение;` без аргумента бросает тот же объект (позиция/стек сохраняются);
  `ВызватьИсключение ИнформацияОбОшибке()` в эталоне создаёт новое исключение (позиция =
  строка перевыброса, исходное — в `Причина`) — наше расхождение (FR-008) осознанно.
- `ИмяМодуля` ошибки = `SourceCode.Name` (для файлов — путь); `ИмяМодуля` **кадра** = 
  `SourceCode.Location`; для файлов совпадают, для динамики расходятся. Мы унифицируем на
  один идентификатор (R4) — расхождение документируется.
- `ИсходнаяСтрока` — **сырая** строка исходника (с отступами, без Trim); у CRLF эталон тащит
  `\r`. Мы `\r` убираем (нормализуем), отступы сохраняем.
- Стек: `[0]` — самый внутренний кадр; последний — кадр тела корневого модуля (в эталоне
  `$entry`). В кадре `НомерСтроки` = строка вызова (для вызывающих) / строка throw (`[0]`).
  Служебных/stdlib-кадров нет. У фонового задания — только его собственные кадры.
- Пустая ошибка вне `Исключение`: `Описание=""`, `НомерСтроки=0`, `ИмяМодуля=""`,
  `ИсходнаяСтрока=""`, `ПодробноеОписаниеОшибки()=""`; `ПолучитьСтекВызовов()` в эталоне —
  `Неопределено` (у нас для реальных ошибок всегда коллекция; для пустой — пустая коллекция;
  расхождение документируется).
- `КраткоеПредставлениеОшибки` = `Описание`; `ПодробноеПредставлениеОшибки` = сообщение +
  «по причине:» для вложенных причин (BSL-стека нет) — у нас не меняем (R7).
- `ПодробноеОписаниеОшибки()` в эталоне = CLR `Exception.ToString()` (непереносимо) — у нас
  описание + BSL-стек (R6).
- `ОписаниеОшибки()` в эталоне для runtime-ошибки имеет вид
  `{Модуль <путь> / Ошибка в строке: N / <текст>}`. **У нас текст `ОписаниеОшибки()` не
  меняется** (точные `toEqual` в тестах, FR-014) — позиция только в полях/подробном
  описании/хостовом выводе. Это расхождение с эталоном, фиксируется в `docs/status.md`.
- Динамический код: эталон даёт `{<путь>}:<строка>:<exec>` и нестабильный `<string hash>` в
  кадре. Мы используем стабильные маркеры `<Выполнить>`/`<Вычислить>` (R9).
- `ИнформацияОбОшибке()` в методе, вызванном из блока `Исключение`, в эталоне пуста (ошибка
  живёт в кадре-обработчике); у нас `ctx.currentError` на уровне модуля — вложенный метод
  видит ошибку. Поведение не меняем (полезнее), при необходимости фиксируем тестом.
- **Критично для реализации**: снимок стека надо делать в момент throw (в самом внутреннем
  `exec`-catch, до pop кадра), а не на верхнеуровневом catch — иначе при `yield*`-раскрутке
  внутренние кадры уже сняты. Ошибки stdlib (обычный `Error`) аннотируются на ближайшей
  BSL-границе (позиция оператора вызова) — аналог `ExternalSystemException`.
- `Параметры`/`Причина` (`Cause`): `Параметры` в объём не входят (как и вложенные причины);
  `Причина` = `Null` (FR-005).

## Открытые вопросы (закрыты)

- Порядок кадров — изнутри наружу (R3).
- Формат `ИмяМодуля` — R4/data-model.
- `ПодробноеПредставлениеОшибки` — не меняем (R7).
- Перевыброс с `ИнформацияОбОшибке` — сохраняем снимок, расхождение (R5).

## Тест-кейсы (основа tasks.md)

1. `1/0` в методе → `НомерСтроки` = строка деления, `ИмяМодуля` = путь, стек: метод → `<модуль>`.
2. Ошибка stdlib (индекс массива) → позиция оператора вызова.
3. `ВызватьИсключение "текст"` → позиция строки `ВызватьИсключение`; `Описание` = текст.
4. `ВызватьИсключение;` после поимки → позиция исходной ошибки.
5. `ВызватьИсключение ИнформацияОбОшибке()` → позиция исходной ошибки (наше решение).
6. Импорт `#Использовать` → `ИмяМодуля` импорта, стек с вызывающим кадром.
7. `Новый Класс(...)` → стек с конструктором.
8. `Выполнить` → `<Выполнить>`, строка фрагмента, кадр вызывающего.
9. Обработчик события/`data-os-*` → позиция обработчика.
10. `Асинх`-метод + `Ждать` → позиция возникновения, кадр async-метода.
11. Фоновое задание → `ИнформацияОбОшибке` со свойствами и стеком.
12. Пустая ошибка вне `Исключение` → пустые поля, пустой массив.
13. Неизменность: точные тексты `ОписаниеОшибки()`/`Описание` (существующие тесты).
14. CLI stderr/exit 1; браузерный `console.error` с `#blockN`.
