# Feature Specification: Фоновые задания (МенеджерФоновыхЗаданий, ФоновоеЗадание, Приостановить)

**Feature Branch**: `feature/async`

**Created**: 2026-11-11

**Status**: Implemented (кооперативная модель; happy-dom + `examples/jobs.html`, ручная приёмка)

**Input**: Пользователь: «Давай отспекаем новую таску… Ждать \ Асинх… В 1с такой
функциональности нет, а то что есть не очень удобное» → уточнение: «я забыл в оскрипте
есть МенеджерФоновыхЗаданий, который решает подобную задачу, и инфраструктура вокруг него.
Давай ее реализуем, а потом поверх этого апи сделаем асинх\ждать. Что бы была обратная
совместимость, и новый функционал».

Эталон: `reference/OneScript/src/OneScript.StandardLibrary/Tasks/*.cs`
(`BackgroundTasksManager`, `BackgroundTask`, `BackgroundTasksRegistry`, `TaskStateEnum`),
глобальная `Приостановить`/`Sleep` — `StandardGlobalContext.cs`; сценарии —
`reference/OneScript/tests/tasks.os`.

**Осознанное расхождение с эталоном** (конституция, принцип I): в эталоне задания — это
настоящие потоки C# (`Task`). В браузере — основной среде продукта — потоков с общими
объектами, модульными переменными и замыканиями нет. Поэтому задания — кооперативные
логические потоки в одном потоке исполнения: переключение происходит в точках ожидания
(`Приостановить`, `Ожидать*`) и по квантам исполнения. Настоящего параллелизма CPU нет,
изоляция данных потоков и блокировки не нужны. Расхождение фиксируется в `docs/status.md`
и закрепляется тестами.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Запустить задание в фоне, дождаться результата, не подвесить страницу (Priority: P1)

Разработчик на странице в `<one-script>` запускает метод текущего модуля как фоновое
задание, сразу продолжает работу (например, обновляет состояние, печатает сообщения) и
затем дожидается задания и читает его результат. Пока задание ждёт (`Приостановить`),
страница продолжает обрабатывать события браузера и таймеры.

**Why this priority**: Это минимальный полезный сценарий: без него фоновые задания не
дают ничего, а без неблокирующего ожидания они нереализуемы в браузере. Всё остальное —
расширения этого сценария.

**Independent Test**: BSL-скрипт создаёт задание на функцию, возвращающую сумму, печатает
маркер сразу после запуска, дожидается завершения и печатает состояние и результат; в
браузерном тесте во время ожидания продолжает тикать таймер страницы.

**Acceptance Scenarios**:

1. **Given** метод-функция возвращает значение, **When** скрипт вызывает
   `ФоновыеЗадания.Выполнить(ЭтотОбъект, "Посчитать", Параметры)` и затем
   `Задание.ОжидатьЗавершения()`, **Then** `Задание.Состояние` = `Завершено`, а
   `Задание.Результат` равен возвращённому значению.
2. **Given** задание запущено на процедуру без результата, **When** ожидание завершено,
   **Then** состояние `Завершено`, `Результат` = `Неопределено`.
3. **Given** после `Выполнить` основной скрипт продолжает печатать сообщения, **When**
   задание ещё активно, **Then** сообщения основного скрипта появляются раньше результата
   задания (основной поток не блокируется запуском).
4. **Given** задание вызывает `Приостановить(200)`, **When** основной скрипт ожидает его
   завершения, **Then** за время ожидания браузер обрабатывает таймеры/события страницы
   (страница не замирает).
5. **Given** в задании возникла ошибка, **When** ожидание завершено, **Then**
   `Состояние` = `ЗавершеноАварийно`, `ИнформацияОбОшибке.Описание` содержит исходный
   текст ошибки, `Результат` = `Неопределено`, а `ОжидатьЗавершения()` возвращает
   `Истина` и не бросает исключение.
6. **Given** `Параметры` не переданы, **When** читается `Задание.Параметры`, **Then**
   значение = `Неопределено`; **Given** передан массив, **When** исходный массив меняют
   после запуска, **Then** задание работает с копией на момент создания.

### User Story 2 - Дождаться группы заданий, любого из них или всех с ошибками (Priority: P2)

Разработчик запускает несколько независимых заданий и управляет ожиданием: ждёт все, ждёт
первое завершившееся, ждёт все текущие и узнаёт об аварийных заданиях. Таймауты позволяют
не зависнуть навсегда.

**Why this priority**: Пакетная работа — типичный сценарий «загрузить N источников»;
без группового ожидания менеджер неудобен. Требует уже работающего одиночного ожидания.

**Independent Test**: BSL-скрипт с тремя заданиями (быстрое, медленное, аварийное)
проверяет `ОжидатьЛюбое` (индекс быстрого), `ОжидатьВсе` с таймаутом (`Ложь`), затем
`ОжидатьЗавершенияЗадач` (исключение с описанием аварийного задания).

**Acceptance Scenarios**:

1. **Given** массив из нескольких заданий, **When** вызывается `ОжидатьВсе(Задания)`,
   **Then** управление возвращается после завершения всех, результат `Истина`.
2. **Given** одно задание ещё не завершилось, **When** `ОжидатьВсе(Задания, Таймаут)`
   исчерпывает таймаут, **Then** возвращается `Ложь`, а задания продолжают выполняться.
3. **Given** массив заданий, **When** `ОжидатьЛюбое(Задания)` завершается, **Then**
   возвращается индекс первого завершившегося задания; при таймауте — `-1`.
4. **Given** `ОжидатьЗавершенияЗадач()` дождался текущих заданий и среди них есть
   аварийные, **When** вызов завершается, **Then** бросается исключение, в описании
   которого перечислены аварийные задания; успешные задания текущего снимка удаляются из
   реестра, аварийные остаются.
5. **Given** таймаут `0`, **When** ожидание выполняется, **Then** оно бесконечно; **Given**
   отрицательный таймаут, **When** ожидание вызывается, **Then** исключение о неверном
   аргументе.
6. **Given** задание уже завершено, **When** вызывается `ОжидатьЗавершения`, **Then**
   возвращается `Истина` немедленно.
7. **Given** пустой массив, **When** вызывается `ОжидатьВсе`, **Then** `Истина`; **When**
   вызывается `ОжидатьЛюбое`, **Then** исключение (как в эталоне/.NET).

### User Story 3 - Реестр заданий, состояния и текущее задание (Priority: P3)

Разработчик ищет задания по состоянию, имени метода, объекту или уникальному
идентификатору, очищает реестр, узнаёт изнутри задания, какое это задание, и понимает,
почему старые задания исчезли из списка.

**Why this priority**: Диагностика и управление нужны, когда заданий много; базовые
сценарии работают и без них.

**Independent Test**: BSL-скрипт создаёт задания разных состояний, проверяет фильтры
`ПолучитьФоновыеЗадания`, `ПолучитьТекущее` изнутри задания и снаружи, `Очистить`,
вытеснение при переполнении реестра.

**Acceptance Scenarios**:

1. **Given** запущены и завершены задания, **When** вызывается
   `ПолучитьФоновыеЗадания()`, **Then** активные идут в порядке запуска, затем завершённые
   в порядке завершения.
2. **Given** фильтр по `Состояние`, `ИмяМетода`, `Объект` или `УникальныйИдентификатор`,
   **When** вызывается `ПолучитьФоновыеЗадания(Фильтр)`, **Then** возвращаются только
   подходящие задания; неизвестные ключи фильтра игнорируются; сравнение имени метода —
   без учёта регистра.
3. **Given** код исполняется внутри задания, **When** вызывается
   `ФоновыеЗадания.ПолучитьТекущее()`, **Then** возвращается это задание; **Given** код
   исполняется в основном потоке, **Then** `Неопределено`.
4. **Given** реестр содержит задания, **When** вызывается `ФоновыеЗадания.Очистить()`,
   **Then** задания пропадают из `ПолучитьФоновыеЗадания` и `ПолучитьТекущее`, но уже
   запущенные дорабатывают и не возвращаются в реестр.
5. **Given** завершённых заданий больше ёмкости реестра (1000), **When** добавляется новое
   задание, **Then** удаляется ранее всех завершившееся; активные задания не вытесняются,
   даже если их больше ёмкости.
6. **Given** код пытается создать `Новый МенеджерФоновыхЗаданий`, **When** он исполняется,
   **Then** исключение: менеджер один и доступен только через глобальное `ФоновыеЗадания`.

### Edge Cases

- Задание запущено, но скрипт завершается раньше него: хост обязан дождаться всех
  запущенных заданий перед завершением запуска, чтобы не потерять вывод и ошибки.
- `Очистить` не отменяет задания: они дорабатывают, но перестают быть видимыми.
- Взаимное ожидание заданий (A ждёт B, B ждёт A) или ожидание задания самим собой не
  обнаруживается — это документированный дедлок (как в эталоне с потоками).
- Модульные переменные и объекты общие для всех заданий: изменения из задания видны
  основному скрипту после ожидания. Одновременная запись из двух заданий — логическая
  гонка на уровне операторов; блокировок в модели нет, и это документируется.
- Долгое вычисление без `Приостановить` не должно надолго замораживать страницу: движок
  периодически уступает управление хосту.
- `Приостановить(0)` уступает управление, не задерживая; отрицательное значение —
  исключение о неверном аргументе.
- Задание на несуществующий/неэкспортный метод, на не-объект или с `Параметры` не-массив —
  понятное исключение в момент `Выполнить`, а не «тихое» задание.
- Аргумент `Длительное` принимается для совместимости, но в кооперативной модели не влияет
  на поведение (нет выделенных потоков).
- Ошибка одного задания не прерывает основной сценарий; она хранится в задании и не
  всплывает в точку ожидания (в отличие от будущего `Ждать`).
- Событие BSL, вызванное внутри задания, доставляется подписчикам в том же логическом
  потоке; порядок подписок сохраняется.
- Таймауты задаются в миллисекундах и приблизительны: ожидание не отменяет задание и не
  гарантирует мгновенного возврата при `0`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Движок ДОЛЖЕН предоставлять глобальное значение `ФоновыеЗадания` /
  `BackgroundJobs` — единственный экземпляр менеджера типа
  `МенеджерФоновыхЗаданий` / `BackgroundTasksManager`. Создание второго менеджера через
  `Новый` НЕ ДОЛЖНО быть возможным.
- **FR-002**: `Выполнить(Объект, ИмяМетода, Параметры = Неопределено, Длительное = Ложь)` /
  `Execute` ДОЛЖЕН проверять аргументы, копировать массив параметров, ставить задание в
  очередь и немедленно возвращать `ФоновоеЗадание`, не блокируя основной поток.
- **FR-003**: `ФоновоеЗадание` / `BackgroundTask` ДОЛЖНО предоставлять свойства
  `УникальныйИдентификатор` / `UUID`, `ИмяМетода` / `MethodName`, `Объект` / `Object`,
  `Состояние` / `State`, `Параметры` / `Parameters`, `Результат` / `Result`,
  `ИнформацияОбОшибке` / `ExceptionInfo` и метод `ОжидатьЗавершения(Таймаут = 0)` /
  `Wait`.
- **FR-004**: Перечисление `СостояниеФоновогоЗадания` / `BackgroundJobState` ДОЛЖНО иметь
  значения `НеВыполнялось` / `NotRunned`, `Активно` / `Active`, `Завершено` / `Completed`,
  `ЗавершеноАварийно` / `Failed`.
- **FR-005**: Жизненный цикл задания: после создания — `НеВыполнялось`; во время
  исполнения — `Активно`; после успеха — `Завершено` с `Результат`; после ошибки —
  `ЗавершеноАварийно` с `ИнформацияОбОшибке`. Значения `Результат` и
  `ИнформацияОбОшибке` по умолчанию — `Неопределено`.
- **FR-006**: Менеджер ДОЛЖЕН предоставлять методы `Очистить` / `Clear`,
  `ОжидатьВсе` / `WaitAll`, `ОжидатьЛюбое` / `WaitAny`,
  `ОжидатьЗавершенияЗадач` / `WaitCompletionOfTasks`,
  `ПолучитьФоновыеЗадания` / `GetBackgroundJobs`,
  `ПолучитьТекущее` / `GetCurrent` с семантикой эталона.
- **FR-007**: Ожидания ДОЛЖНЫ поддерживать таймаут в миллисекундах: `0` — ждать
  бесконечно, отрицательное значение — исключение; `ОжидатьВсе` возвращает `Булево`
  (успели/не успели), `ОжидатьЛюбое` — индекс завершившегося элемента или `-1` при
  таймауте, `ОжидатьЗавершения` — `Булево`.
- **FR-008**: `ОжидатьЗавершенияЗадач` ДОЛЖЕН ждать снимок заданий реестра и, если среди
  них есть аварийные, бросать исключение с перечислением аварийных заданий; успешные
  задания снимка удаляются из реестра, аварийные — остаются.
- **FR-009**: Реестр ДОЛЖЕН хранить активные задания в порядке запуска, завершённые — в
  порядке завершения; ёмкость по умолчанию — 1000; при переполнении вытесняются ранее
  всех завершившиеся, активные не вытесняются. `ПолучитьФоновыеЗадания` ДОЛЖЕН
  поддерживать фильтр по `Состояние`, `ИмяМетода`, `Объект`, `УникальныйИдентификатор`,
  игнорировать неизвестные ключи и сравнивать имена методов без учёта регистра.
- **FR-010**: Глобальная функция `Приостановить(Миллисекунды)` / `Sleep` ДОЛЖНА
  приостанавливать текущий логический поток исполнения, не блокируя хост (в браузере —
  страницу); она работает и в основном скрипте, и в задании.
- **FR-011**: Модель исполнения — кооперативная: задания разделяют модульное состояние и
  объекты, переключаются в точках ожидания и по квантам; настоящего параллелизма нет;
  изоляция данных потоков, `ТекущийПоток` и `БлокировкаРесурса` НЕ входят в объём.
- **FR-012**: Хост-интеграция: скрипт без операций ожидания исполняется синхронно, как
  сейчас; скрипт с ожиданием возвращает хост-среде управление по Promise-контракту, и
  хост (`<one-script>`, CLI, `runScript`) дожидается завершения запуска и всех запущенных
  заданий. `Сообщить` продолжает выводить в `console.log` по мере выполнения.
- **FR-013**: Поверхность ДОЛЖНА работать одинаково в браузере и Node; ядро не
  импортирует Node-модули и не обращается к DOM напрямую.
- **FR-014**: Все новые имена (глобальное значение, методы, свойства, перечисление и его
  значения, глобальная функция) ДОЛЖНЫ поддерживать русский и английский варианты.
- **FR-015**: Обратная совместимость: скрипты и JS-вызовы без фоновых заданий/ожиданий
  сохраняют прежнее поведение; существующие тесты и сборка остаются зелёными; новых
  зависимостей нет.
- **FR-016**: Ошибки ДОЛЖНЫ быть понятными и локализованными: неверный таймаут,
  `Параметры` не-массив, цель не BSL-объект, метод не найден или не экспортный,
  не-задание в массиве ожидания, пустой массив для `ОжидатьЛюбое`.

### Key Entities

- **МенеджерФоновыхЗаданий** — единственный экземпляр, доступный как `ФоновыеЗадания`:
  создаёт задания, хранит реестр, управляет ожиданиями и сообщает текущее задание.
- **ФоновоеЗадание** — handle запущенного метода: идентификатор, объект и имя метода,
  параметры, состояние, результат, информация об ошибке, ожидание завершения.
- **СостояниеФоновогоЗадания** — состояние жизненного цикла задания.
- **Логический поток исполнения** — исполняемый контекст основного скрипта или задания;
  в кооперативной модели один физический поток, переключение только в точках ожидания и
  по квантам.
- **Реестр заданий** — упорядоченный список активных и завершённых заданий с ёмкостью и
  вытеснением.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 20 заданий, каждое с `Приостановить(100)`, завершаются все вместе заметно
  быстрее последовательных 2 секунд (цель — менее 1 секунды), результаты всех заданий
  корректны — проверяется таймером теста.
- **SC-002**: Браузерная страница остаётся отзывчивой: за время задания в 500 мс хост
  успевает обработать не менее 10 таймеров, а при длинном вычислении без
  `Приостановить` — не менее 5 (кванты). Проверяется браузерным тестом.
- **SC-003**: 100% аварийных заданий имеют непустое `ИнформацияОбОшибке.Описание`;
  ошибки заданий не прерывают основной сценарий и не роняют хост.
- **SC-004**: Все сценарии реестра и ожиданий проходят: фильтры (4 ключа), порядок,
  `Очистить`, вытеснение при 1001 завершённом задании (остаётся 1000, вытеснено самое
  раннее), активные не вытесняются.
- **SC-005**: `pnpm typecheck` и `pnpm test` зелёные; `dist/onescript.js` собирается;
  старые скрипты и тесты не изменили поведение; новых зависимостей нет.
- **SC-006**: Приёмочный сценарий в браузере: `<one-script>` запускает задание, печатает
  маркер до результата, дожидается и печатает результат; страница при этом остаётся
  отзывчивой (happy-dom-тест + ручная проверка на `examples/`).
- **SC-007**: Не менее 15 BSL-сценариев из `reference/OneScript/tests/tasks.os`, входящих
  в объём (создание, состояния, результат/ошибка, ожидания, поиск, `Очистить`, порядок),
  воспроизведены и проходят; сценарии, требующие настоящих потоков, явно исключены.

## Assumptions

- Принято решение: кооперативная однопоточная модель (вариант без Web Workers). Следствие:
  нет истинного параллелизма CPU, `ТекущийПоток`, `БлокировкаРесурса`, изоляция данных
  потоков, обработчики завершения потока и дочерние процессы — вне scope. Это
  фиксируется в `docs/status.md`.
- Ёмкость реестра фиксирована (1000, как `DefaultCapacity` эталона); настройка
  `backgroundJobs.capacity` вне scope, пока в проекте нет системы настроек.
- `Длительное`/`longRunning` принимается для совместимости сигнатуры и не влияет на
  исполнение: выделенных потоков в модели нет.
- `Параметры` передаются по значению (копия массива на момент `Выполнить`); значения
  элементов — те же объекты, как в эталоне для потока.
- Ошибки задания трактуются как BSL-ошибки исполнения (любое исключение внутри задания);
  `ИнформацияОбОшибке` даёт `Описание`/`ПодробноеОписаниеОшибки`; полноценный стек вызовов
  задания — отдельная будущая работа.
- Порядок запуска заданий — FIFO; порядок переключения между активными заданиями не
  гарантируется, гарантируется лишь отсутствие длительной блокировки хоста.
- BSL-события, подписки и `ЭтотОбъект` общие для заданий; события, вызванные в задании,
  доставляются в том же логическом потоке.
- Фаза 2 (`Асинх`/`Ждать`, объект `Обещание`) строится поверх этого API отдельной
  спецификацией: задания дают handle/состояние/результат/ошибку, а `Ждать` будет
  приостанавливать текущий логический поток до завершения задания. Синтаксис и
  диагностика `Асинх`/`Ждать` уже есть в парсере эталона; в этой спеке они не входят.
- Неблокирующий HTTP (`fetch`), отмена заданий, приоритеты и планировщик с несколькими
  очередями — вне scope этой спеки.
- Браузерные тесты — happy-dom; приёмка в реальном браузере — ручная на `examples/`
  (Playwright — спека 007).
