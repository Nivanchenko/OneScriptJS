# Research: Упрощённая директива #Использовать

**Date**: 2026-11-11 | **Plan**: [plan.md](plan.md) | **Spec**: [spec.md](spec.md)

Контекст: движок — синхронный tree-walking интерпретатор (`src/runtime/interpreter.ts`);
`run()` вызывает `tokenize → preprocess → parse → Interpreter.run`. Сейчас `#Использовать`
целиком отбрасывается препроцессором и не несёт семантики. Браузерная точка входа
(`src/browser/onescript.ts`) исполняет `<one-script>` синхронно; серверных API, кроме
`console.log`, нет. Эталон (`reference/OneScript/src`) реализует библиотеки через
`LibraryManager` и `ScriptDrivenObject`, но наша версия осознанно упрощена до файлов.

## R1. Синхронное исполнение + предзагрузка исходников

**Decision**: движок остаётся синхронным. Загрузка источников — отдельная фаза,
выполняемая платформой до вызова `run()`: Node читает файлы синхронно, браузер
асинхронно скачивает дерево импортов через `fetch`. В `run()` передаётся готовая карта
«разрешённый путь → исходник» (`RunOptions.modules`).

**Rationale**: `run()` используется синхронно в `<one-script>`, CLI, `runScript` и во всех
300 тестах; делать интерпретатор async — значит переписать публичный API и всю батарею
тестов ради одной директивы. Предзагрузка сохраняет детерминизм: к моменту исполнения
первой строки все исходники уже на месте, а I/O-ошибки возникают до запуска, а не в
середине вычислений.

**Alternatives considered**:
- *Async-интерпретатор / async `run()`* — ломает контракт `<one-script>` и CLI, заражает
  `Interpreter` асинхронностью; отвергнуто.
- *Синхронный XHR в браузере* — устаревший API, блокирует поток, не работает на главном
  потоке в современных браузерах; отвергнуто.
- *`import()`/ES-модули для `.os`* — абсолютно другая модель загрузки, BSL-файлы не JS;
  отвергнуто.

## R2. Извлечение импортов — в препроцессоре, а не в лексере/парсере

**Decision**: `src/parser/preprocessor.ts` получает `preprocessScript(tokens)` →
`{ tokens, imports: ImportDirective[] }`. Директивы собираются тем же проходом, который
уже вычисляет `#Если`, поэтому импорт в неактивной ветке не попадает в список. Текст
директивы разбирается: имя директивы, затем строка в кавычках (с `""`), хвостовой
`//`-комментарий отбрасывается. Директива без кавычек импортом не считается.
Существующий `preprocess(tokens)` остаётся обёрткой и возвращает только токены.

**Rationale**: `#Использовать` — препроцессорная директива (`LanguageDef.cs`:
`WordType.Preproc`), лексер уже отдаёт её одним токеном. Сбор в том же проходе, что и
`#Если`, бесплатно даёт FR-014 («неактивные ветки не грузятся») и сохраняет позицию
строки для диагностики. Парсеру импорт не нужен: это не AST-узел, а метаданные файла.

**Alternatives considered**:
- *Отдельный повторный проход по токенам* — дублирует логику условий и позиций; отвергнуто.
- *AST-узел `UseDirective`* — тянет импорт в интерпретатор и платформенный I/O; отвергнуто.
- *Оставить no-op* — не выполняет задачу.

## R3. Вид скрипта: модуль или класс — по наличию конструктора

**Decision**: после разбора файла `kind = 'class'`, если среди верхнеуровневых
`MethodDeclaration` есть `ПриСозданииОбъекта`/`OnObjectCreate` (без учёта регистра),
иначе `'module'`.

**Rationale**: прямое требование спеки; проверка по AST не требует новых ключевых слов и
отдельного синтаксиса. Эталон ищет конструктор так же — по билингвальному имени
(`UserScriptContextInstance.OnInstanceCreationTerms`).

**Alternatives considered**:
- *Расширение файла / маркер в комментарии* — новый синтаксис, которого нет в BSL;
  отвергнуто.
- *Наличие `Экспорт` у чего угодно* — не различает модуль и класс; отвергнуто.

## R4. Семантика класса: тело модуля исполняется на каждый экземпляр

**Decision**: при `Новый Класс(...)` создаётся новый `Interpreter`, исполняется всё тело
файла (инициализация `Перем` и код вне методов), затем вызывается
`ПриСозданииОбъекта`. При импорте класса тело не исполняется и экземпляр не создаётся.

**Rationale**: это модель эталона для сценария-объекта: `ScriptDrivenObject.Initialize` →
`OnInstanceCreation` → исполнение `ModuleBody`, затем `UserScriptContextInstance` вызывает
конструктор. Она же даёт независимое состояние экземпляров: у каждого свой
`moduleScope`, а не общая копия. Для модуля-синглтона тело исполняется один раз в
`ModuleLoader`.

**Alternatives considered**:
- *Тело один раз при импорте, копирование состояния в экземпляр* — ненаблюдаемо
  отличается для побочных эффектов (Сообщить, счётчики) и расходится с эталоном;
  отвергнуто.
- *Тело при каждом обращении к экземпляру* — ломает состояние; отвергнуто.

## R5. Кеш рантайма и циклы: запись `loading` до исполнения тела

**Decision**: `ModuleLoader` держит `Map<разрешённый путь, CacheEntry>`; запись создаётся
до рекурсивной загрузки зависимостей и исполнения тела, состояние `loading` → `ready`.
Повторный импорт того же пути возвращает существующую запись. Обращение к члену
`loading`-модуля бросает `Модуль '<имя>' ещё загружается (циклический импорт)`.
При ошибке импорта запись удаляется, ошибка пробрасывается.

**Rationale**: кеш до исполнения — единственный способ разорвать A↔B без стека и без
повторного исполнения. Ранний доступ к недоинициализированному модулю не может работать
корректно, поэтому явная ошибка лучше `Неопределено` (FR-013). Кеш живёт в `ModuleLoader`,
который создаётся на один вызов `run()`; два `<one-script>` и два запуска независимы.

**Alternatives considered**:
- *Глобальный кеш процесса* — протекает между тестами и страницами, противоречит FR-011;
  отвергнуто.
- *Разрешать цикл «пустым» модулем без ошибки* — тихое `Неопределено` contradicts FR-013;
  отвергнуто.

## R6. Разрешение путей и имя модуля

**Decision**: путь разрешает платформа через функцию `resolve(importPath, importerPath)`,
передаваемую в `RunOptions`:
- Node: `path.isAbsolute(p) ? path.normalize(p) : path.resolve(path.dirname(importer), p)`;
- браузер: `new URL(p, importerUrl).href` (относительный — от URL документа, `/` — от
  корня origin);
- ядро (тесты без платформы): нормализация posix-пути `сегменты + ..` без обращения к ФС.

Имя — последний сегмент разрешённого пути, у которого отброшен `.os` (регистронезависимо)
или последнее расширение; проверяется на BSL-идентификатор. Кеш ключуется разрешённым
нормализованным путём.

**Rationale**: `node:path` и `URL` — стандартные средства платформ, свои велосипеды не
нужны. Один и тот же путь в разных написаниях нормализуется до одного ключа (FR-011).
Ядро не импортирует `node:path` (принцип II конституции).

**Alternatives considered**:
- *Резолвить в ядре вручную для всех сред* — не покрывает Windows-диски и URL-семантику;
  отвергнуто.
- *Ключ — исходная строка директивы* — дублирует загрузку при `./m.os` и `m.os`; отвергнуто.

## R7. Модуль и класс в реестре `GlobalContext`

**Decision**:
- модуль: `ctx.registerGlobal(имя, BslModule)` (доступ как к переменной) **и**
  `ctx.registerType(имя, () => { throw ... })`, чтобы `Новый Модуль` давал понятную ошибку
  «модуль не является классом»;
- класс: `ctx.registerType(имя, factory)` (для `Новый`) и `ctx.registerGlobal(имя,
  BslClassRef)`, чьи `getProp`/`callMethod` бросают «класс не является модулем»;
- коллизия имени с существующим типом/глобалом или с другим файлом — ошибка до
  исполнения тела.

**Rationale**: разрешение идентификатора уже умеет `env.resolveGlobal`, а `Новый` —
`env.construct`; регистрация в обе таблицы использует существующие механизмы без правок
парсера. Sentinel-объекты дают точные сообщения вместо «Свойство недоступно для
Неопределено». `GlobalContext` дополняется `hasType`/`hasGlobal` для проверки коллизий.

**Alternatives considered**:
- *Только global для модуля и только type для класса* — `Новый Модуль` и `Класс.Метод`
  дают невнятные ошибки; отвергнуто.
- *Новый реестр имён в интерпретаторе* — дублирует `GlobalContext`; отвергнуто.

## R8. Экспортная поверхность: метаданные AST + API интерпретатора

**Decision**: `VariableDeclaration` получает `exportedNames?: string[]` (парсер уже
вызывает `matchKeyword(KW_EXPORT)`, но результат выбрасывает). `Interpreter` хранит
`exportedVars` в `Ctx` и получает методы:
`hasExportedMethod/callExportedMethod`, `hasExportedVar/getExportedVar/setExportedVar`,
`hasConstructor`, `getMethod(name)`. `BslModule`/`BslInstance` реализуют `BslObject` через
эти методы; `typeName` — имя файла.

**Rationale**: минимальная правка AST (новое необязательное поле не ломает существующие
тесты), а вся проверка экспорта — в одном месте рантайма. `getMethod` нужен и для
арности конструктора, и для сообщений.

**Alternatives considered**:
- *Сделать `names` массивом `{name, exported}`* — ломает существующий тест и всех
  потребителей AST; отвергнуто.
- *Проверять экспорт по исходнику регуляркой* — хрупко; отвергнуто.

## R9. Диагностика

**Decision**: тексты ошибок фиксируются контрактом
([contracts/use-directive-contract.md](contracts/use-directive-contract.md)): отсутствующий
файл/URL, ошибка разбора вложенного файла с его путём, недопустимое имя, конфликт имён,
циклический доступ, неверная арность конструктора, класс-как-модуль, модуль-как-класс.

**Rationale**: FR-018 требует называть путь/имя; тесты должны проверять сообщения, а не
только факт исключения. Стиль — существующий (`Метод 'X' не найден у типа Y`,
`Свойство 'X' не найдено…`); арность конструктора — по эталону
(`Параметры конструктора: необходимых параметров: N, передано параметров M`).

**Alternatives considered**:
- *Английские тексты* — проект русскоязычный, существующие ошибки русские; отвергнуто.

## R10. Браузерная интеграция

**Decision**: `src/browser/module-source.ts` — `preloadModuleSources(entrySource, entryUrl):
Promise<Map<string, string>>`: обходит директивы, `fetch` каждого URL, сканирует
полученные исходники, кеширует по `href`. `connectedCallback` выполняет асинхронную
подготовку, затем синхронный `run(...)`. Ошибки загрузки/исполнения выводятся в
`console.error`. Тест — happy-dom + заглушка `fetch`.

**Rationale**: `fetch` — стандартный браузерный способ получить файл, как для `<script>`;
URL-резолвинг нативный. `run` остаётся синхронным, поэтому существующие тесты и
декларативные обработчики не меняются. Явный `console.error` выполняет FR-017 и не
оставляет unhandled rejection.

**Alternatives considered**:
- *Встроить загрузку в `run`* — потребует async во всём ядре (R1); отвергнуто.
- *Требовать предварительной сборки модулей в бандл* — противоречит «как js/картинки»;
  отвергнуто.

## R11. Динамическая загрузка и прочие точки входа

**Decision**: `ЗагрузитьСценарийИзСтроки`/`ЗагрузитьСценарий` не учат импорт: карты
исходников у них нет, а путь неизвестен. Директивы с путём там остаются no-op;
`shortcut: динамическая загрузка не резолвит #Использовать, апгрейд — при появлении
требования`. Node `runScript(source)` без базового пути тоже не грузит файлы: при наличии
импорта `ModuleLoader` бросает «исходник не найден»; CLI использует полноценный загрузчик.

**Rationale**: спека не требует импорта из динамических сценариев; добавлять ещё один
источник правды — лишний код. Основной пользовательский путь (файл/страница) покрыт.

**Alternatives considered**:
- *Передавать loader в `ЗагрузитьСценарийИзСтроки`* — расширение публичного API без
  требования; отложено.
