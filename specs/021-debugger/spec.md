## Зачем

Сейчас (после спеки 020) runtime-ошибки BSL несут модуль, строку и BSL-стек — но нет
интерактивной отладки: нельзя поставить точку останова, выполнить шаг, посмотреть переменные
в остановленном кадре, вычислить выражение. Отладчик — следующий логичный слой после
инфраструктуры снимка ошибок; значительная часть фундамента (кадры, идентификаторы
источников) уже построена в 020.

Цель: **DAP-совместимый отладчик для BSL** в VS Code:
- Node CLI (launch) — вспомогательная среда;
- браузер (attach к странице с `<script type="text/osjs">`) — основная среда проекта;
- без переписывания движка: интерпретатор уже генераторный, пауза — это `yield`.

## Пользовательские сценарии и тестирование

### User Story 1 - Отладка Node-скрипта из VS Code (Priority: P1)

Разработчик открывает `.osjs` в VS Code, ставит брейкпоинт на строку, запускает конфигурацию
`launch` (тип `osjs`) и останавливается на строке; видит BSL-стек, локальные и модульные
переменные, может шагать (`next`/`stepIn`/`stepOut`/`continue`), вычислить выражение в
остановленном кадре.

**Independent Test**: запустить отладчик на фикстуре с вложенными методами; проверить
последовательность остановок, стек, переменные, evaluate — без браузера.

### User Story 2 - Отладка в браузере: attach к странице (Priority: P1)

Разработчик поднимает dev-сервер, запускает конфигурацию `attach` (URL страницы), открывает
страницу; брейкпоинты в `examples/*.osjs`/inline-блоках срабатывают, стек/переменные
доступны; `Сообщить()` и `console.log` идут в Debug Console; страница не «висит» на паузе
(движок уступает event loop).

**Independent Test**: страница с внешним `.osjs` и inline-блоком; проверить брейкпоинт в
обоих, остановку, стек, продолжение; без VS Code — через прямой DAP-клиент/тест.

### User Story 3 - Брейкпоинты в inline-блоках HTML (Priority: P2)

Разработчик ставит брейкпоинт на строку внутри `<script type="text/osjs">` в HTML-файле;
отладчик останавливается на соответствующей строке HTML, показывает её в редакторе.

**Independent Test**: HTML-фикстура с двумя блоками; брейкпоинт в каждом; проверка
маппинга HTML-строка ↔ блок-строка (переиспользовать `src/lsp/html-blocks.ts`).

### User Story 4 - Условные брейкпоинты, logpoints, исключения (Priority: P2)

Условный брейкпоинт останавливается только при истинном условии; logpoint печатает
выражение без остановки; фильтр исключений (`uncaught`/`all`) останавливает на ошибке до
её обработки/выхода.

**Independent Test**: BSL-фикстуры с условиями/логами/исключениями.

### User Story 5 - Async-методы и фоновые задания (Priority: P3)

Остановка внутри `Асинх`-метода и в фоновом задании; DAP `threads` показывает логические
потоки; `pause` останавливает исполнение; переменные задания доступны.

**Independent Test**: BSL-скрипт с `Асинх`/`Ждать` и с фоновым заданием.

### Edge Cases

- Пауза при исполнении без брейкпоинтов (`pause` request) — движок должен уступать event loop.
- Пауза в момент DOM-события: пока скрипт стоит, страница жива; новые BSL-входы
  (`data-os-*`, BSL-события) не должны «уезжать» вперёд — их нужно гейтить.
- Evaluate в остановленном кадре не должен ломать стек/состояние; повторный evaluate.
- Брейкпоинт на строке, где нет оператора (`иначе`, `Перем` верхнего уровня, многострочное
  выражение) — привязка к ближайшему оператору или `verified: false`.
- Ошибка/исключение в момент старта страницы (до подключения отладчика) — страница уже
  исполнилась; нужен понятный сценарий «перезагрузите страницу»/attach-до-загрузки.
- Остановка в импортированном модуле/классе/`Выполнить`/`Вычислить`.
- Остановка при `Сообщить()`/`console.log` — вывод не должен теряться.
- Несколько вкладок/страниц — только одна сессия отладки (как в эталоне).
- HTTPS-страница и `ws://localhost` — mixed content (ниша; dev-сервер http).
- Скрипт вызывает `process.exit`/закрывает страницу — сессия корректно завершается.
- Глубокий стек/рекурсия — не должно ломать DAP stackTrace.

## Требования (черновые)

- **FR-001**: Расширение VS Code ДОЛЖНО регистрировать тип отладчика `osjs` с конфигурациями
  `launch` (Node CLI) и `attach` (браузер, URL).
- **FR-002**: ДОЛЖЕН существовать DAP-адаптер (Node, stdio), реализующий подмножество DAP:
  `initialize`, `launch`/`attach`, `setBreakpoints`, `setExceptionBreakpoints`,
  `configurationDone`, `threads`, `stackTrace`, `scopes`, `variables`, `evaluate`,
  `continue`, `next`, `stepIn`, `stepOut`, `pause`, `disconnect`, события `initialized`,
  `stopped`, `continued`, `output`, `terminated`, `exited`.
- **FR-003**: Брейкпоинты по файлу/строке для `.osjs`; для HTML — внутри
  `<script type="text/osjs">` с маппингом на строки HTML; для внешних `.osjs` в браузере —
  маппинг URL ↔ файл рабочей области (`webRoot`/`url`).
- **FR-004**: Шаги: `next` (через вызовы, на той же глубине), `stepIn`, `stepOut`,
  `continue`, `pause`; семантика должна работать через `yield`/async и не ломать
  синхронный быстрый путь при выключенном отладчике.
- **FR-005**: `stackTrace` — BSL-кадры (метод, модуль, строка), изнутри наружу; кадр 0 —
  текущий; кадры импортов/классов/динамики.
- **FR-006**: `scopes`/`variables` — локальные переменные кадра, модульные переменные,
  переменные `ЭтотОбъект` (по возможности); значения BSL визуализируются (примитивы,
  коллекции; таблицы значений — минимум/позже).
- **FR-007**: `evaluate` в остановленном кадре (и `watch`/`hover` через него) — выражение
  BSL в области видимости кадра; ошибки evaluate не ломают сессию.
- **FR-008**: Условные брейкпоинты (`condition`) и logpoints (`logMessage`) — P2.
- **FR-009**: Фильтры исключений: `uncaught` (и, если получится, `all`); остановка до
  обработки/выхода с корректным стеком (использовать снимок ошибки из 020).
- **FR-010**: Потоки: главный скрипт + фоновые задания; `pause` — согласованно (стоп всех
  логических потоков); DAP `threads`/`stopped(threadId)`.
- **FR-011**: Браузерный транспорт: page-agent ↔ адаптер по локальному WebSocket (fallback —
  SSE/long-poll); агент подключается до исполнения блоков и ждёт `configurationDone`;
  production-бандл `dist/onescript.js` не должен тянуть отладочный клиент.
- **FR-012**: Вывод `Сообщить()`/`console.log`/`console.error` идёт в DAP `output`
  (Debug Console), не теряется на паузе.
- **FR-013**: При выключенном отладчике поведение движка не меняется: синхронный скрипт
  остаётся синхронным, производительность не деградирует (проверяется существующими
  тестами).
- **FR-014**: Документация: README/`docs/` — как запускать отладчик; при появлении
  BSL-видимого API отладчика — `docs/reference.md` + каталог API.
- **FR-015**: Тесты: unit для контроллера отладки/шагов/брейкпоинтов; integration для DAP
  (stdio/in-memory); browser-agent тесты; e2e Playwright — опционально (спека 007 пока не
  реализована).

## Вне объёма (черновой scope)

- Компиляция BSL → JS и source maps (не тот путь: tree-walking интерпретатор).
- Полный DAP (data breakpoints, memory, profiling, hot reload).
- Удалённая отладка не с localhost.
- Отладка C#-OneScript (у него свой адаптер/протокол).
- `Параметры`/вложенные причины ошибок (не связано с отладчиком).
- Многосессионность/несколько вкладок одновременно (как в эталоне — одна сессия).

## Ключевые сущности

- **Сессия отладки** — одно подключение DAP-клиента к адаптеру (Node launch или browser attach).
- **Источник** — идентификатор модуля из 020 (`RunOptions.sourceId`, путь/URL/`<Выполнить>`/
  `<blockN>`), плюс текст для отображения.
- **Кадр BSL** — метод/модуль/строка + область видимости (для variables/evaluate).
- **Точка останова** — файл+строка (+ условие/лог), с маппингом на источник движка.
- **Поток** — главный интерпретатор или фоновое задание (`forkForJob`).
- **Контроллер отладки** — общий объект на `RuntimeEnvironment`, включающий хук, паузу,
  брейкпоинты, шаги, реестр потоков/источников.

## Критерии успеха (черновые)

- **SC-001**: В VS Code можно запустить `launch` Node-скрипт, остановиться на брейкпоинте,
  увидеть стек/переменные, шагнуть и продолжить — без правок скрипта.
- **SC-002**: В браузере (dev-сервер) attach работает для внешнего `.osjs` и inline-блока;
  страница не зависает на паузе; остальные блоки ждут продолжения.
- **SC-003**: При выключенном отладчике `pnpm typecheck && pnpm test` зелёные, синхронный
  быстрый путь не изменился.
- **SC-004**: Evaluate и условные брейкпоинты работают в остановленном кадре; ошибки
  evaluate не роняют сессию.
- **SC-005**: Документация и `pnpm build` зелёные; `.vsix` собирается с адаптером.

## Ограничения (конституция/AGENTS.md)

- Браузер — основная среда; ядро без `node:*`/DOM; отладочный транспорт/адаптер — в
  `src/node`/`extensions/vscode`.
- TDD; перед «готово» — `pnpm typecheck && pnpm test`, при изменении сборки/API — `pnpm build`,
  `pnpm check:docs`, `pnpm typecheck:vscode`.
- Новые зависимости только с обоснованием (вероятные кандидаты: `@vscode/debugadapter` +
  `@vscode/debugprotocol`, `ws`; альтернатива — свой DAP-слой и SSE).
- Коммиты — только по явной просьбе; работа в feature-ветке.

## Открытые вопросы (для `/speckit-clarify`)

1. **Приоритет MVP**: Node launch first или сразу browser attach? (Рекомендация: Node launch —
   дешёвый спайк; browser attach — основная ценность, но дороже.)
2. **Запуск браузера**: attach-only (пользователь открывает страницу) или адаптер сам
   запускает Chrome? (Рекомендация: attach-only в MVP; launch через CDP/`openExternal` позже.)
3. **Inline HTML-блоки** в MVP или P2? (Рекомендация: P2, после внешних `.osjs`; маппинг уже
   есть в `src/lsp/html-blocks.ts`.)
4. **Зависимости**: допустимы ли `@vscode/debugadapter`/`ws`? (Рекомендация: да, с
   обоснованием в плане; DAP-слой и транспорт — не писать с нуля без нужды.)
5. **BSL-видимый API отладчика** (`Отладчик.Остановиться`, `ТочкаОстанова` и т.п.) — нужен?
   (Рекомендация: вне MVP.)
6. **Потоки/пауза**: останавливать все логические потоки или только текущий? (Рекомендация:
   все — предсказуемее; задания показывать как потоки.)
7. **Условные брейкпоинты/logpoints** в MVP или P2? (Рекомендация: P2.)
8. **Исключения**: только `uncaught` в MVP? (Рекомендация: да; `all` — позже.)
9. **Node-адаптер**: движок в процессе адаптера или отдельный child-процесс? (Рекомендация:
   в процессе для MVP, child — если понадобится изоляция `process.exit`.)
10. **Virtual sources** для `Выполнить`/`Вычислить`: показывать как `<Выполнить>` в DAP
    или не открывать? (Рекомендация: показывать в стеке, отдельные виртуальные документы —
    позже.)

## Предлагаемый план (подробнее — context.md)

Этап 0 — спайк: хук + контроллер + сырой DAP (Node, брейкпоинт/шаг/стек/locals/evaluate).
Этап 1 — VS Code Node launch + сборка `.vsix`.
Этап 2 — browser attach (внешние `.osjs`, WS, webRoot-маппинг).
Этап 3 — inline HTML-блоки.
Этап 4 — conditions/logpoints, exceptions, jobs, визуализация коллекций.
Этап 5 — тесты/доки/edge cases/финальная верификация.
Оценка: MVP (0–2) ≈ 9–14 человеко-дней, полностью ≈ 18–29; см. context.md.
