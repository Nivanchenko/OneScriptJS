# Feature Specification: Формат `.osjs` — отделение от ванильного OneScript

**Feature Branch**: `master`

**Created**: 2026-11-11

**Status**: Implemented

**Input**: Позиция владельца проекта: «os — движок на C#, чужой проект, там свои линтеры и
всё своё. osjs — наш движок, для фронтенда; наша целевая платформа — браузер. Мы не
пытаемся поддержать и заменить C#-движок. Но у пользователей обоих движков в одном
проекте могут быть файлы обоих типов, и я не хочу путаницы»; уточнение: «блокировать на
входе не нужно».

## Context

В экосистеме есть два независимых движка одного языка:

- **Ванильный OneScript** (`reference/OneScript/`, C#) — бэкенд, формат **`.os`**, свои
  линтеры и инструменты (в VS Code `.os` заявляет расширение `1c-syntax.language-1c-bsl`,
  оно же запускает `oscript -check`).
- **OneScriptJS** (этот репозиторий, TypeScript) — целевая платформа **браузер**, формат
  **`.osjs`**, своя стандартная библиотека и свои расширения диалекта (`Асинх`/`Ждать`).

Решение: файлы OneScriptJS используют `.osjs`, файлы ванильного OneScript остаются `.os` и
нам не принадлежат. Движок по-прежнему исполняет `.os` (грамматика BSL общая, эталонный
корпус `reference/OneScript/tests/*.os` — внутренняя проверка поведения), но блокировать
его на входе не нужно: это не улучшает изоляцию, зато ломает собственный регресс и
миграцию пользователей.

Почему суффикс, а не настройка: в VS Code `contributes.languages` не имеет приоритетов —
при двух претендентах на один суффикс побеждает зарегистрировавшийся последним, молча.
Разделение суффиксов убирает конфликт по конструкции: `.os` остаётся у чужого расширения,
`.osjs` — у нашего, в смешанном проекте обе цепочки инструментов работают независимо.
Дополнительно `.osjs` даёт свободу менять диалект, не выдавая это за совместимость с C#,
и позволяет в будущем диагностировать `[Node]`-API как ошибку в браузерных файлах.

`.ojs` не используется: суффикс занят расширением для ObservableHQ-ноутбуков. `.jsos` не
используется: читается хуже.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Смешанный проект: файл сам говорит, чей он (Priority: P1)

В одном проекте лежат бэкендовые `.os` (ванильный OneScript) и фронтендовые `.osjs`
(OneScriptJS). Разработчик открывает `.osjs` и получает инструменты нашего движка; открывает
`.os` — инструменты ванильного OneScript. Никакой борьбы за один и тот же language id нет,
и чужой линтер не проверяет фронтенд-файлы.

**Why this priority**: Это исходная боль пользователя и главная причина решения.

**Independent Test**: `.os` и `.osjs` в одном каталоге; каждый открывается своим
инструментом; `oscript -check` не видит `.osjs`. Без установленного редакторного расширения
проверяется тем, что суффиксы не пересекаются: у `.osjs` нет ни одного чужого претендента.

**Acceptance Scenarios**:

1. **Given** в проекте `backend/main.os` и `frontend/app.osjs`, **When** открыт `app.osjs`,
   **Then** его обрабатывает инструментарий OneScriptJS, а `.os`-линтер к нему не
   применяется.
2. **Given** файл `.os` из чужого движка, **When** пользователь работает с ним, **Then**
   мы его не переименовываем, не подсвечиваем своим расширением и не ломаем его линтер.

---

### User Story 2 - Наши файлы, примеры и документация — `.osjs` (Priority: P2)

Разработчик видит единую конвенцию: наши скрипты, примеры в `examples/`, команды и
документация используют `.osjs`, а `.os` упоминается только как чужой формат.

**Why this priority**: Конвенция без примеров не приживается; новые файлы копируют
окружение.

**Independent Test**: `examples/modules.html` исполняется в браузере и печатает ожидаемые
значения; поиск по своим tracked-файлам не находит `.os` вне упоминаний чужого формата.

**Acceptance Scenarios**:

1. **Given** страница `examples/modules.html`, **When** она открыта в браузере, **Then**
   `#Использовать "lib/Модуль.osjs"` и `#Использовать "lib/Приветствие.osjs"` работают,
   вывод совпадает с документированным.
2. **Given** новый пример или тест, **When** он добавляется, **Then** его файлы названы
   `.osjs`.

---

### User Story 3 - `osjs`-движок принимает `.os` без блокировки (Priority: P3)

Пользователь прогоняет ванильный `.os` через наш движок (эталонный корпус, миграция,
отладка) — файл исполняется, отказ или предупреждение не выдаются.

**Why this priority**: Блокировка — собственный вред без выгоды; изоляция достигается
конвенцией и редакторными инструментами, а не запретом.

**Independent Test**: `pnpm oscript reference/OneScript/tests/array.os` и `#Использовать`
на `.os`-файл работают; CLI не проверяет расширение.

**Acceptance Scenarios**:

1. **Given** `.os`-скрипт, **When** он передан CLI, **Then** движок исполняет его как
   обычный BSL-скрипт.
2. **Given** `.osjs`-файл с `#Использовать "lib/Модуль.osjs"`, **When** скрипт исполняется
   в Node или браузере, **Then** модуль загружается, имя модуля — имя файла без последнего
   расширения.

---

### Edge Cases

- `.os`, переданный CLI: исполняется без предупреждений (сознательно, FR-002).
- `.osjs` импортирует `.os`: технически работает (общий загрузчик), конвенция рекомендует
  импортировать `.osjs`; принудительной проверки в этой спеке нет.
- Регистр расширения: `.OSJS` специально не распознаётся; файловая система case-sensitive,
  автоматики нет.
- Эталонный корпус `reference/OneScript/tests/*.os` не переименовывается и не изменяется.
- Устаревший `dist/` не обновляется вручную — он пересобирается.

## Requirements *(mandatory)*

- **FR-001**: Файлы OneScriptJS ДОЛЖНЫ использовать расширение `.osjs`: переименовать
  `examples/lib/Модуль.os` → `.osjs`, `examples/lib/Приветствие.os` → `.osjs`; обновить пути
  `#Использовать` в `examples/modules.html`; примеры в README.
- **FR-002**: `.os` — чужой формат: ДОЛЖЕН не блокироваться CLI и загрузчиком, не
  переименовываться и не заявляться нашим редакторным инструментом.
- **FR-003**: `#Использовать` ДОЛЖЕН работать с `.osjs` в Node и браузере; имя модуля —
  имя файла без последнего расширения (существующая семантика темы 008 не меняется).
- **FR-004**: Конвенция ДОЛЖНА быть зафиксирована в `AGENTS.md` (§1 и правило 10), `README.md`,
  `docs/architecture.md`, `docs/status.md`.
- **FR-005**: `src/node/cli.ts`, `src/runtime/module-objects.ts` (комментарий) и
  `scripts/copy-examples.mjs` ДОЛЖНЫ упоминать `.osjs`; `pnpm oscript --help` показывает
  `<файл.osjs>`.
- **FR-006**: `reference/**/*.os` НЕ ДОЛЖНЫ изменяться; расширение файла не влияет на
  грамматику и рантайм: `.os` и `.osjs` разбираются и исполняются одинаково.
- **FR-007**: Грамматика BSL не меняется; редакторное расширение, подсветка и LSP — вне
  объёма этой спеки (отдельная работа).
- **FR-008**: Новых зависимостей и изменений публичного API нет.

### Key Entities

- **`.osjs`** — наш формат: исходник для OneScriptJS; браузерная стандартная библиотека
  и наши расширения диалекта.
- **`.os`** — чужой формат: исходник ванильного C#-OneScript для бэкенда; эталонный корпус
  для сверки поведения.
- **Редакторный language id** — в будущем `osjs` только для `*.osjs`; `*.os` остаётся у
  чужого расширения.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `grep -r '\.os\b'` по нашим tracked-файлам находит `.os` только в местах,
  где речь о чужом формате/эталоне (README — блок «Форматы файлов», `docs/status.md`,
  `reference/`, исторические спеки 001–008).
- **SC-002**: `examples/modules.html` в браузере печатает `Сложить(2, 3) = 5`,
  `Поле = 10`, `Поле после записи = 99`, `Привет, Никита`.
- **SC-003**: Тест в `tests/browser-modules.test.ts` загружает модуль `.osjs` по URL и
  получает значение (браузер — основная целевая среда).
- **SC-004**: `pnpm typecheck && pnpm test && pnpm check:docs` зелёные; новых зависимостей
  нет.
- **SC-005**: `pnpm oscript <файл.osjs>` и `pnpm oscript <файл.os>` исполняют скрипт
  (ручная проверка станет возможна после `pnpm build` — на `dist/`).
- **SC-006**: `docs/status.md` содержит строку спеки 013, а `AGENTS.md` — правило 10.

## Assumptions

- Паритет с C#-эталоном остаётся **способом проверки поведения** (конституция, принцип I),
  а не продуктовым обещанием заменить C#-движок; эталонный корпус — внутренний регресс.
- Расширение файла — маркер владения и целевой платформы, а не переключатель диалекта:
  парсер одинаков для `.os` и `.osjs`.
- Автоматическая миграция чужих проектов и проверка импортов между форматами не делаются;
  конвенция достаточна на этом этапе.
- Редакторное расширение появится отдельно (grammar-only, затем error-recovery и
  in-process LSP-провайдеры — см. исследование в обсуждении); до его появления `.osjs`
  остаётся без подсветки, и это осознанно.
- `.osjs` в статическом хостинге работает без настройки MIME: браузерный загрузчик читает
  ответ через `response.text()` и не смотрит `Content-Type`.

## Следующая работа (вне объёма 013): линтер / language server / плагин VS Code

Зафиксировано по итогам обсуждения формата — чтобы не потерять. Это **заметка, а не
спецификация**: анализ, план и задачи будут отдельной спекой, когда дойдём.

**Что нужно.** Для `.osjs` сейчас нет ни подсветки, ни проверок — чужие инструменты этот
формат не знают. В итоге нужны:

- подсветка `.osjs` в VS Code (TextMate-грамматика + `language-configuration.json`);
- линтер/диагностика — ошибки разбора и очевидные проблемы прямо в редакторе;
- language server: автокомплит (ключевые слова, глобальные функции/типы stdlib, члены
  объектов), hover; позже — переходы и символы документа;
- возможно, отдельный плагин VS Code: наш language id `osjs`, только `*.osjs`.

**Почему так.** `.osjs` — наш собственный формат (см. выше): чужие линтеры и грамматики
не должны его трогать, а `.os` мы не заявляем — борьбы за один суффикс нет.

**До чего договорились в обсуждении (контекст, не план):**

- Лексер и парсер на TypeScript уже есть в движке (`src/lexer`, `src/parser`) — LSP логично
  писать на TS и переиспользовать их, а не брать второй парсер (tree-sitter) и не писать
  анализатор заново.
- Порядок: сначала грамматика (подсветка, скобки, `//`, фолдинг `#Область` — это работает
  без LSP), затем диагностика и провайдеры. Грамматику можно взять за основу из
  MIT-грамматики 1c-syntax с переименованием scope в `source.osjs`.
- Для автокомплита главный блокер — парсер: сейчас он кидает исключение на первой ошибке,
  а в AST нет `end`-позиций. Полный репарс файла дёшев (замер ~1.7 мс на 1000 строк),
  поэтому инкрементальность не нужна; нужны error-recovery и `span` в AST.
- Отдельный процесс сервера не обязателен: можно начать с in-process провайдеров VS Code,
  а stdio-LSP добавить позже для Neovim/Zed.
- Оценки из обсуждения (не обязательство): grammar-only расширение — 1–3 дня; полезный
  минимум с диагностикой и автокомплитом — ~6–10 дней, а не 4–6 недель.
- Чего не делать сразу: semantic tokens, go-to-definition, форматирование, tree-sitter,
  скачивание внешнего сервера в рантайме.
- Пока редакторных инструментов нет, `.osjs`-файлы остаются без подсветки — это осознанно.
